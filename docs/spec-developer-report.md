# 仕様: 「質問・要望」ボタン（利用者からの質問・追加要望・不具合報告。旧称「要望・報告」←「開発者へ報告」）

- 正本: この文書。実装は `src/utils/operationTrace.ts` / `src/utils/developerReport.ts` /
  `src/components/developer-report/DeveloperReportModal.tsx` / `functions/src/developerReport.ts`(＋`index.ts` の
  `submitDeveloperReport`) / `tools/developer-report-notify.mjs` / `.github/workflows/developer-reports.yml`。
- 決定日: 2026-09-04（オーナー指示）。背景: 室長から「この一ヶ月でバグがあったが忙しくて自分で対処した」と後から
  連絡があり、何が起きたか追えなかった。**忙しくてもボタン1つ・数秒で開発者へ知らせられる**導線を用意する。

## A. 目的と非目的

- 目的: 利用者が「おかしいな」と感じた瞬間に、**直近の操作履歴と画面のデータ**を開発者へ届け、
  バグ／仕様の誤解／勘違いを開発者側で切り分けられるようにする。
- **受け取った後の進め方（オーナー指示 2026-09-04・厳守）**: 利用者報告 Issue を見ても**勝手に修正を始めない**。
  調査・整理までは進めてよいが、コード修正への着手はオーナーが確認して許可してから。
- 非目的: 全操作をサーバーへ**常時**記録すること（コストとノイズが見合わない。オーナー判断 2026-09-04）。
  **2026-10-22 改定（オーナー採用「即時対応のための案 2」）**: 常時送信はしないまま、**保存リクエストに「前回保存以降の痕跡」を相乗りさせて**サーバーへ残す（追加リクエスト無し・§D-3）。
  本番での不変条件(INV)自己検査（オーナー判断で不要。報告が来たら開発者が検査する）。

## B. ボタンの位置と見え方（オーナー確定）

- ボタン名は **「質問・要望」**（オーナー指示 2026-09-14。旧「要望・報告」＝2026-09-04 確定）。質問・追加要望・不具合を同じ導線で送る。
- **種類の並びは 質問 → 要望 → 不具合**、モーダルを開いたときは**質問が選ばれている**（オーナー指示 2026-09-14）。
  サーバー／`normalizeDeveloperReportCategory` の不正値の丸め先は従来どおり `bug`（表示の既定とは別物）。
- 「テスト送信のときは内容に『#テスト』と書いてください」の**案内文はモーダルから削除**（オーナー指示 2026-09-14）。
  `#テスト` を含めたときのテスト扱い（§C）は残る。
- 盤面・日程表の見た目以外（メール件名 `[コマ表アプリ 要望・報告]`・送信元表示名・Issue ラベル）は**変えていない**
  （開発者側の受信フィルタを壊さないため）。
- **コマ表(盤面)**: ツールバーの「講師日程共有」の**右**に「質問・要望」。同じ形(secondary/slim)で**色だけ変える**
  (淡いオレンジ・`report-developer-button`)。テンプレ編集モードでは出さない（講師日程共有と同じ）。
- **日程表(別タブ・生徒/講師)**: ツールバーの「登録された講習期間を表示する」の**右**に「質問・要望」。
  同じ枠線ボタンで色だけ変える(`button.report-developer`)。印刷用全員表示(all-view)には出さない（ツールバー自体が無い）。
- 日程表は**操作せず表示だけ見て**「おかしい」と思うことがある。そのため日程表側のボタンは、その日程表で
  表示していた条件（種別・期間・講習期間ラベル・選択人物・検索語）を報告に添える。
- **モーダルは盤面・日程表で同一の表示・文言**（オーナー指示 2026-09-04）。文言の正本は
  `DEVELOPER_REPORT_UI_TEXT`（`src/utils/developerReport.ts`）で、日程表 HTML の埋め込みスクリプトへ生成時に埋め込む。
  大きく読みやすく（幅 820px・本文 17px・入力欄 7 行）。一言が空なら送信せず「一言を入力してください」と促す。

## C. 送信内容（`submitDeveloperReport`）

| 項目 | 内容 | 出どころ |
|---|---|---|
| 種類 | 不具合(bug) ／ 要望(request) ／ 使い方の質問(question・2026-09-13 実装。§G)。既定は bug（画面の表示名は 2026-10-10 に「不具合・おかしい」「追加してほしい・要望」から短縮。送る値は不変） | 同一モーダルのラジオ |
| 内容 | **必須**（2026-09-04 改定・空欄は送れない。上限 2000 字） | 盤面・日程表とも同一モーダルの textarea |
| テスト扱い | 内容に `#テスト`（または `#test`）を含むと **Issue を起票しない**（`notifiedAt` を即時に埋める）。メールは【テスト】付きで届く | サーバーが判定 |
| 直近の操作痕跡 | 端末内リングバッファの最新 300 件 | `operationTrace.ts`（§D） |
| 報告時点の教室データ | メモリ上の教室データ（**未保存の変更込み**）を gzip して Storage へ | `buildClassroomSnapshotPayload` |
| メタ | 教室・報告元(board/schedule)・アプリ版数・UA・URL・画面・未保存有無・最終保存時刻 | App |
| 添付画像（2026-10-14・**2026-10-22 一般モーダルにも**） | 画面側で長辺 1600px の JPEG に縮め data URL で送る（1 枚 1.5MB・合計 6MB まで。サーバーも同じ上限で検証し超過分は捨てる）。**枚数は教室で分ける**: 開発用教室の確認リストは 1 通 8 枚、**一般の質問・要望モーダルは 3 枚**（オーナー決定 2026-10-22「3 枚に絞る」・`resolveDeveloperReportAttachmentLimit`）。付け方（オーナー決定 2026-10-22・案 A）: **盤面**＝「画面を撮る」（html2canvas でいま見えている範囲を撮る・モーダルと確認リストは写さない・`screenCapture.ts`）＋「画像を選ぶ」＋スクリーンショットの貼り付け（Ctrl+V）、**日程表タブ**＝「画像を選ぶ」だけ（埋め込み JS で縮小し postMessage で本体へ・本体が同じ規則で再検証）。**メールには 1 枚目だけ 1MB まで添付**し、残りは Storage の置き場所を本文に書く | `DeveloperReportModal` / `scheduleHtml.ts` → `attachments` |
| 実行者・受領時刻 | **サーバーが付ける**（自己申告にしない） | Cloud Function |

- 保存先: Firestore `workspaces/{ws}/developerReports/{reportId}`（メタ＋操作痕跡）、
  Storage `developer-reports/{ws}/{classroomId}/{reportId}.json.gz`（教室データ）。
  添付画像は同じフォルダに `{reportId}-img{n}.{jpg|png|webp}`（n は 1 から）で置き、文書の `attachments[]`
  （label=項目 id・name・mimeType・byteLength・storagePath）に保存できた分だけ残す（画像本体は Firestore に入れない）。
  開発ダッシュボードの報告詳細と確認リスト読み取りツールは保存先を表示するだけ（読むのは読み取り専用トークンで Storage から）。
- **本番データ（classroomSnapshots 等）には一切書かない。** 権限は保存と同じ `requireClassroomAccessMember`。
- 教室データの Storage 保存に失敗しても報告本体は残す（`snapshotStoragePath` 空・`snapshotByteLength=-1`）。

## D. 操作痕跡（端末内・全操作）

- 対象: 盤面が変わる全確定（`commitWeeks` の前後差分＝「日付 限 机番: 前 → 後」）、テンプレ反映(board-rebuild)、
  undo/redo、保存の成否、操作ログ(`operationLog.ts`)のイベントの写し、日程表など別タブからの postMessage、
  報告モーダルの開閉・送信結果。
- 保持: 教室ごとに最新 **1000 件**（2026-10-22 に 300 → 1000・案 2）をメモリ＋`localStorage`(`operation-trace:<classroomId>`)。再読み込みを跨いで残る。報告に同梱するのは新しい方から 300 件（不変）。
- **端末外へ出るのは「報告ボタン」と「保存」の 2 経路だけ**（2026-10-22 改定・§D-3。それ以前は報告のみ）。記録の失敗は本体の操作に影響させない（例外は握る）。
- 操作ログ（サーバー監査記録・在庫が減る/記録が消える操作だけ）とは別物。両者の種別一覧はサーバー
  `DEVELOPER_REPORT_TRACE_KINDS` と二重管理（テストで一致を固定）。

### D-2. 画面エラーの自動捕捉と自動報告（2026-10-22 オーナー採用「即時対応のための案 3」）

- `window` の未捕捉例外（`error`）・未処理の Promise 拒否（`unhandledrejection`）・React の描画例外（`main.tsx` の `AppErrorBoundary`）を
  `src/utils/clientErrorCapture.ts` が捕まえ、(1) 操作痕跡に **kind `error`** で残し（両側の種別一覧に追加）、(2) 教室を開いていれば
  **「質問・要望」と同じ経路（`submitDeveloperReport`・種類 bug）で自動報告を 1 通送る**。利用者の操作は要らない。
- 本文の先頭行は目印 **`[自動エラー報告]`**（クライアント `CLIENT_ERROR_AUTO_REPORT_MARKER`／サーバー `DEVELOPER_REPORT_AUTO_ERROR_MARKER`・テストで一致）。
  サーバーは `isAutoErrorReport: true` で記録し、**メールは送る（件名【自動エラー報告】）が GitHub Issue は作らない**（`notifySkipped: 'auto-error'`・
  同じエラーが複数端末から届いて Issue が増えるのを防ぐ）。開発ダッシュボードの「通知済みだが Issue なし」に出る。室長の「これまでの質問と回答」には出さない。
- 歯止め: 同じエラー（出どころ・名前・文の先頭・最初のフレーム）は 1 回、**1 タブ 3 通まで**。旧チャンク掴み（`recoverFromChunkLoadError` が扱う）・
  `ResizeObserver loop`・中身の無い `Script error.` は送らない（痕跡にも残さない）。
- 描画例外の受け皿（`AppErrorFallback`）は室長向けの案内（「内容は開発者へ自動で届いています」「再読み込み」）だけを出し、内部語を出さない。
- 日程表タブ（独立 HTML）のエラーは対象外（別タブの `window`）。

### D-3. 操作痕跡の保存同梱（2026-10-22 オーナー採用「即時対応のための案 2」）

- 保存リクエスト（`saveClassroomSnapshot`）に **前回保存以降の痕跡**（新しい方から最大 300 件・`collectOperationTraceSinceLastSave`）を `operationTrace` として相乗りさせる。
  サーバーは報告と同じ規則（`normalizeDeveloperReportTrace`）で正規化し、`classroomSnapshots/{classroomId}/operationTraces/{saveId}`
  （`entries`・`entryCount`・`firstAt`／`lastAt`・`snapshotVersion`・`recordedAt`）へ残す。**書けなくても保存本体は成功のまま**（操作ログと同じ方針）。
- 「どこまで載せたか」の印（最後に載せた痕跡の時刻）は**保存が成功したときだけ進め**、`localStorage`（`operation-trace-saved:<classroomId>`）にも残す。
  失敗した保存の分は次の保存にもう一度乗る（文書 id は saveId なので重複にはならない）。
- 保持 **90 日**（`OPERATION_TRACE_RETENTION_DAYS`・掃除は `cleanupOldSaveAttempts` の対応表）。保存ごとの教室版履歴（`docs/spec-save-restore.md` §8-1 #14）と
  同じ saveId・版数で突き合わせ、`tools/snapshot-diff.mjs` の前後比較と並べて読む。

## E. 開発者が受け取る仕組み

- **メール即時通知（オーナー要望 2026-09-04・LINE の代替）**: Cloud Function `notifyDeveloperReportByMail` が
  `developerReports` 文書の作成をトリガに SMTP で送る。本文は**開発者がいま見るべきものだけ**（オーナー指示 2026-10-22・確認リスト
  v1.5.625 qa-ai-3「多くのことが書かれすぎていてわかりにくい」）: 教室／種類・報告元／時刻・版・報告者の 3 行、内容、添付、
  （質問）AI の自動回答、「次にすること」1 行、受付番号＋Firestore パスの 1 行。**操作痕跡は不具合の報告だけ**（直近 20 件・生徒名を含む・
  私的経路なので可）。要望・質問には載せない。Firestore コンソールの URL・gsutil コマンド・「進め方」の長文・保存状態の行（不具合以外）は
  2026-10-22 に外した。全文（操作痕跡 全件・教室データ・AI の記録）は開発ダッシュボード（§E-3）で読む。純関数 `buildDeveloperReportMail` /
  `buildDeveloperReportMailNextStepLines`（`functions/src/developerReport.ts`）。
  設定は functions runtime env（ローカル `functions/.env`・CI は repo secret `PROD_FUNCTIONS_ENV`）の
  `REPORT_MAIL_SMTP_URL`（例: `smtps://you%40gmail.com:アプリパスワード@smtp.gmail.com:465`）と `REPORT_MAIL_TO`
  （任意 `REPORT_MAIL_FROM`）。未設定なら送らず `mailSkipped` を記録。成否は文書の `mailSentAt` / `mailError`。
  手順は `docs/runbooks/monitoring.md`。**GitHub の通知設定は不要**（Issue はあくまで課題管理の記録）。

- `.github/workflows/developer-reports.yml` が **15 分ごと**に `notifiedAt == null` の報告を Firestore REST で拾い、
  GitHub Issue を起票（ラベル `type:bug` / `status:triage` / `source:user-report`）→ `notifiedAt`・`issueNumber` を埋める。
  開発者は GitHub 通知（メール/アプリ）で受け取る。認証は既存 secret `RE_FIREBASE_SERVICE_ACCOUNT`。
- **公開リポジトリのため Issue 本文に操作痕跡（生徒名）・教室データは載せない。** メタ＋一言＋置き場所
  （Firestore 文書パス／Storage パスと取得コマンド）だけ。Issue 本文にも「勝手に修正を始めない・許可後に着手」を明記。
- LINE 通知は **不採用**（オーナー判断 2026-09-04: Messaging API の取得条件が厳しくなったため。メール直送へ置換）。
- **添付画像はメールに 1 枚目だけ（1MB まで）添付**（オーナー決定 2026-10-22）。読めなくても本文は送る。残りの画像は本文に Storage の置き場所を書く（`buildDeveloperReportMailAttachmentLines`）。
- **画面エラーの自動報告（§D-2）は Issue を作らない**（メールのみ・`notifySkipped: 'auto-error'`）。
- Issue のラベルは種類で変える: bug → `type:bug`、request → `type:feature`、question → `type:question`（共通 `status:triage` / `source:user-report`）。
  Issue タイトルの種別は `[利用者報告]` / `[利用者要望]` / `[利用者質問]`。メール件名は質問のとき `【質問】` を先頭に付ける（テスト送信は `【テスト】【質問】` の順）。
- Firestore ルール: `developerReports` は開発者のみ read、write は不可（Cloud Function は Admin SDK で書く）。
  ルールの反映は `firebase deploy --only firestore:rules`（main マージでは反映されない）。

## E-3. 開発ダッシュボード（開発者画面のサブページ・2026-09-25 オーナー指示）

- 目的: 開発者が **会社（workspace）・教室ごとの質問・要望の状況／開発の段階／確認リストの確認済み・未確認** を

## F. 受け入れ条件（テストで固定）

- 一言が空なら盤面・日程表とも送れない（`validateDeveloperReportNote`。本体側でも日程表経由の空文を弾く）。
- 操作痕跡は上限件数・上限文字数で切り、教室未登録なら記録しない（別教室混入防止）。

- サーバーは壊れた要素だけ捨てて残りを通し、`classroomId` は権限確認済みの値を使う。
- Issue 本文に生徒名（操作痕跡）・メールアドレスが載らない。起票→記録の順で二重起票を防ぐ。
- 日程表 HTML にボタンと送受信の両メッセージ種別が含まれ、埋め込みスクリプトが構文的に妥当。
- 種類 `question`（§G・2026-09-13 実装）は client（`DEVELOPER_REPORT_CATEGORIES` / `categoryOptions`）・server（正規化・メール件名【質問】）・
  Issue（ラベル `type:question`・タイトル `[利用者質問]`）の全経路で認識され、client と server の種別一覧はテストで一致を固定する

## G. 質問（種別 `question`）

### G-1. 位置づけ（オーナー確定 2026-09-12・変更不可）

- 種別は **不具合(bug) ／ 要望(request) ／ 質問(question)** の 3 つ。**3 種別とも扱いは同じ**:
  **送信 → ストック（Firestore `developerReports`）→ メール通知 → 後で開発者が対応**。
  質問だけの特別な即時処理（自動応答・AI 即答）は**作らない**。
  **例外: 開発用教室に限り AI 即時回答を試験する（§G-7・オーナー指示 2026-09-14）。本番教室では従来どおり作らない。**
- **当面 API は使わない**（外部 AI への自動連携をアプリ／Cloud Functions から行わない）。
- **利用者への即答はしない。** 利用者が見られるのは**開発者が承認した回答だけ**（§G-3）。
- **AI には全データを渡す**（伏字化・除外はしない。§H-1）。**まとめ読みの実行頻度は決めない。**
- 非目的: 質問の自動分類・自動回答・類似 QA の即時提示（Q-8。§G-4 の基準が確定するまで保留）。

### G-2. 種別の追加位置（Q-2）

既存の導線・モーダル・通知はすべて**流用**する（新しい画面・新しいボタンを増やさない＝学習コストを上げない）。

| 触る場所 | 追加内容 |
|---|---|
| クライアント型 `src/utils/developerReport.ts` | `DEVELOPER_REPORT_CATEGORIES` に `'question'` を追加。既定は **`bug` のまま**（`normalizeDeveloperReportCategory` の既定値を変えない） |
| モーダル文言 `DEVELOPER_REPORT_UI_TEXT.categoryOptions` | 3 番目に `{ value: 'question', label: '使い方の質問' }`。**並び順は 不具合 → 要望 → 質問**（既存 2 つの順序と表示は変えない） |
| 日程表の埋め込みモーダル（`scheduleHtml.ts`） | 同じ文言正本から生成されるため、ラジオが 3 つになるだけ。**盤面と日程表で同一の表示・文言**（§B の原則を維持） |
| サーバー `functions/src/developerReport.ts` | 受け入れ種別に `question` を追加（二重管理はテストで一致を固定＝既存作法） |
| GitHub Issue ラベル | bug → `type:bug`／request → `type:feature`／**question → `type:question`**（共通 `status:triage` / `source:user-report` は据え置き） |
| メール件名 | 種別の接頭辞を付ける。質問は **【質問】**（テスト送信の【テスト】表記は既存どおり併記。実装: `【テスト】【質問】[コマ表アプリ 要望・報告] …` の順） |
| `#テスト` 扱い | 3 種別共通で既存どおり（Issue 起票なし・メールは届く） |

- 質問でも**操作痕跡・教室データのスナップショットは同じように添付**する（「どの画面を見て疑問に思ったか」が
  回答の前提になるため。除外しない）。
- 利用者への表示上の注意書きとして、質問を選んだときだけ**「回答は開発者が確認してからお返しします（すぐには返りません）」**を
  モーダルに出す（即答の期待を作らないため。文言正本は `DEVELOPER_REPORT_UI_TEXT`）。

### G-3. 回答フローと状態遷移（Q-5）

`developerReports/{reportId}` に回答用フィールドを足す（**既存フィールドは変更しない**）。

| 状態 | 条件（文書の状態） | 利用者から見えるか |
|---|---|---|
| **未回答** | `answerDraft` なし・`answeredAt` なし | 見えない |
| **回答案あり** | `answerDraft` あり・`answeredAt` なし | **見えない**（下書きは端末へ一切出さない） |
| **承認済み（返答済み）** | `answerFinal` ＋ `answeredAt` ＋ `answeredBy` あり | **見える**（§G-5 の通知経路のみ） |
| **QA 公開（任意）** | 上に加えて `qaEntries/{id}` が存在し `publishedAt` あり | 全教室（既定・仮置き ③）から閲覧可 |

- 遷移は**一方向**（未回答 → 回答案あり → 承認済み → 任意で QA 公開）。承認済みを未回答へ戻さない。
  内容を直すときは**承認済みのまま本文を更新**し（`answeredAt` は更新、`answerRevision` を +1）、
  返答通知を**再度未読にしない**（利用者を驚かせない）。
- 承認・公開の確定は **callable `answerDeveloperReport`（`requireDeveloperMember`）だけ**が書く。
  クライアントからの `developerReports` 直書きは従来どおり不可（§E のルール踏襲）。
- 承認画面（開発者画面のサブページ `'questions'`）は**一覧＋1 件表示**。1 件ごとに
  「AI 用プロンプトをコピー（1 件分のパック）」「回答案欄」「承認して返答」「QA として公開（既定 OFF）」を置く。
- **質問以外（bug / request）にも同じ回答欄を使ってよい**（「直しました」「要望として登録しました」を返せる）。
  ただし返答は任意で、既定は返さない（§E の「勝手に修正を始めない」と矛盾しないよう、**着手の約束をしない**文面にする）。

- サブページ名は `'answers'`「**質問への回答**」（`src/components/developer-admin/DeveloperReportAnswerScreen.tsx`）。入口は開発者画面右上のボタン。
  一覧（教室・未回答/回答済み/すべて で絞る・新しい順・テスト送信と確認リストは除く）＋1 件表示＋回答欄＋**§G-4 の基準を 1 つのチェックで確認**
  → 「回答を送る」。**「回答案（answerDraft）」の段・「AI 用プロンプトをコピー」・「QA として公開」は作っていない**（書いた回答をそのまま送る）。
- 状態は **未回答 → 回答済み** の 2 つ（`answerFinal` / `answeredAt` / `answeredBy` / `answerRevision` を `developerReports/{id}` に merge・既存フィールドは触らない）。
  再送は改訂（revision +1）で、室長側の既読を未読へ戻さない（`functions/src/reportAnswers.ts planReportAnswerWrite` がテストで固定）。
- 送信可否は純関数 `checkReportAnswerSubmit`（空・4000 字超・基準未確認・同じ本文の再送は止める）。

**解決済み（v1.5.570・2026-09-28・オーナー指示「回答だけでなく解決済みボタンも設けて対応完了したのがわかるように。解決済みは室長側には非表示でOK」）**:
- 回答とは**独立した開発者の対応完了の印**。LINE など画面の外で対応を終えた報告を、回答を書かずに「未回答」から外すために使う。

- 記録は callable **`resolveDeveloperReport`**（`requireDeveloperMember`）が `developerReports/{reportId}` に `resolvedAt` / `resolvedBy` を merge するだけ
  （戻すと両方 null）。回答フィールド・室長側の `reportAnswers` には**触らない** ＝ **室長の画面には出ない**（履歴は回答が無ければ「回答待ち」のまま・未読バッジも変わらない）。
- 一覧の絞り込みは「未回答／回答済み／**解決済み**／すべて」。解決済みは未回答・回答済みに出さない。状態表示は解決済みを最優先（回答があれば「解決済み(回答あり)」）。
  純関数 `filterReportsForAnswering` / `formatReportAnswerRowStatus`（`src/utils/developerReportAnswers.ts`）・`planReportResolveWrite`（`functions/src/reportAnswers.ts`）でテスト固定。

### G-4. 「公開してよい回答」の基準（叩き台・オーナー確定待ち＝仮置き ②）

利用者へ返す**回答本文の内容基準**。**AI へ渡す入力の制限ではない**（入力は §H-1 のとおり無制限）。
承認画面のチェックリストとして出し、**全項目を満たすものだけ「承認して返答」できる**。

1. **個別教室の中身に触れない**… 他教室はもちろん、当該教室の生徒名・講師名・具体的な配置内容を回答本文に書かない
   （「◯◯さんの 9/3 の振替は〜」ではなく「振替が未消化に戻らない場合は〜」と一般化する）。
   **例外（AI 即時回答・妥協案 B・オーナー採用 2026-10-16 夜）**: 利用者の質問文に**名前が出た生徒**については、クライアントが
   権威関数で計算した台帳から抜いた**残数・日付・科目・回数だけ**（§G-7「質問に名前が出た生徒の数字」）を使って具体的に答えてよい。
   講師名・質問に出ていない生徒の名前・他の生徒の配置内容は従来どおり書かない（機械検査「他の生徒」で止める）。
2. **他教室の名前・事例を出さない**… 「他の教室では〜」を書かない（教室間の情報遮断は本アプリの前提）。
3. **未リリース機能・時期を約束しない**… 「次の更新で直します」「来週対応します」と書かない。
   「要望として記録しました」「確認中です」までにとどめる（§E の裁量を保つ）。
4. **料金・契約・請求に触れない**… 費用や契約条件の質問は「開発者から個別に連絡します」と返す（回答本文で確約しない）。
5. **操作手順は現行の実装で再現できるものに限る**… 推測で手順を書かない。`docs/user-manual.md` または
   `docs/spec-*.md` に根拠がある内容だけを書く（根拠が無ければ「確認して改めて回答します」）。
6. **データの復元・削除など不可逆操作を利用者に指示しない**… 復元・ロールバックは開発者が行う前提
   （`docs/runbooks/rollback.md`）。手順を回答本文で教えない。
7. **個人情報・認証情報を含めない**… メールアドレス・UID・トークン・Storage パス・文書 ID を本文に書かない。

- 上の 1〜7 は **QA 公開（§G-6）の前提条件でもある**（公開は「返答可」よりさらに厳しく、
  **特定の教室でしか成り立たない前提を含まない**ことを追加で満たすこと）。
- 判断に迷うものは**公開しない**（既定 OFF）。基準の改定はオーナー承認事項とする。
