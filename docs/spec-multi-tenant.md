- **正本**: この文書。`docs/spec-index.md` の 12 ドメイン正本とは**直交する横断層**（`spec-invariants.md` と同じ扱い）。
  会社（テナント）の境界・開発用教室の識別・越境の遮断・運用ツールの棟指定を定義する。
- **起案日**: 2026-09-16（Phase 0 T0-1）。**根拠**: 計画 `docs/plan-2026-09-15-multi-company-architecture.md`
  （§2 判定基準／§4 DB を分けない設計／§6 問題点 15 件／§7 段階計画／§9 オーナー回答／§10 オーナー質疑の確定値）。

  詳細は各 Phase の仕様追補で確定する（**この文書で未定義を勝手に埋めない**）。
- **背景**: 本アプリは「1 社（既存運営会社）の 3 教室」を前提に育ってきたが、Firestore の最上位は最初から
  `workspaces/{workspaceKey}` であり、rules・callable・定期関数はすべて workspace 単位で書かれている。
  複数会社を同じ Firebase プロジェクトで受け入れるにあたり、**「会社の壁がどこで担保されるか」を仕様として
  明文化し、名前一致・既定値・暗黙の `main` 前提といった「未定義の温床」を Phase 0 で塞ぐ**のが本書の目的。
- **実装との対応**（Phase 0 時点）: `src/utils/developmentClassroomRegistry.ts`（新設・T0-2）／
  `src/utils/developmentClassroom.ts`／`functions/src/developmentClassroomIdentity.ts` ＋ `functions/src/generated/`／

## 0. 用語（この文書の言葉づかい）

| 用語 | 定義 |
|---|---|
| **会社** | 本アプリを契約して使う事業者。**データ上は `workspaces/{workspaceKey}` 1 件と 1 対 1 で対応する**。 |
| **workspace（棟）** | `workspaces/{workspaceKey}` 文書とその配下一式。会社の比喩として「棟」と呼ぶことがある（会話用の別名で、コード上の識別子は常に `workspaceKey`）。 |
| **workspaceKey** | workspace のドキュメント ID。フロントは**ビルド時に `VITE_FIREBASE_WORKSPACE_KEY` で焼き込む**（UI から選べない・現状維持）。 |
| **既存運営会社** | 現在稼働中の会社。workspaceKey は **`main`**。**改名移行はしない**（オーナー確定 2026-09-16・計画 §9-2）。 |
| **会社名** | **棟の文書 `workspaces/{workspaceKey}` のフィールドに持つ**（項目は Phase 3 で確定）。既存運営会社の会社名は「スクールIE」**ではない**ため、コード・文書・コミットメッセージで既存運営会社を「スクールIE 社」と呼ばない（「スクールIE」は教室の屋号であり、教室データ `ClassroomSettings.scheduleHeader` の値）。 |
| **教室** | `workspaces/{workspaceKey}/classrooms/{classroomId}`。室長（manager）は 1 人 1 教室。 |
| **コア** | 全会社で共通の実装（§2 の判定でコアに分類されるもの）。本リポジトリが唯一の出所。 |
| **会社固有** | 会社ごとに差し替えてよい部分（ブランド・呼称・機能の既定 ON/OFF・帳票の注記・追加画面）。Phase 1 で `src/company/` に集約する。 |
| **開発用教室** | その会社で**書き込みを伴う検証をしてよい教室**。§4 のレジストリに登録された `kind: 'development'` の 1 件。 |
| **サンドボックス教室** | 開発用教室に準じて扱う追加の検証用教室（`kind: 'sandbox'`）。 |

> 用語の注意：`company` / `organization` / `tenant` という識別子はコード・データに**存在しない**（計画 §1-8）。
> 新設するとしても **Phase 1 の会社レイヤ（`src/company/`）に限る**。Firestore のパスや保存データの形に
> 「会社」を表す新しい階層を足さない（会社 ＝ workspace で十分に表現できる）。

## 1. テナントモデル（会社の壁はどこにあるか）

### 1-1. データ配置

1. **会社に属するデータはすべて `workspaces/{workspaceKey}/...` の配下に置く**（教室メタ・スナップショット・
   設定・請求月・在籍数台帳・開発者報告・保護者連絡など）。新しいコレクションを足すときも**必ずこの配下**に置く。
2. **トップレベルのコレクションは例外**であり、新設には「未認証の一般公開経路が必要」という正当化が要る
   （QR 提出 `lectureSubmissions`・講師日程共有 `boardShares`・保護者トークン `studentPortalTokens`）。
   この場合でも**文書に `workspaceKey` フィールドを持たせ、どの会社のものか自明にする**（§5-3）。
3. Storage のバックアップは `workspace-auto-backups/{workspaceKey}/...`（既存どおり・workspace 別）。

### 1-2. 所属（members）

1. 権限は `workspaces/{workspaceKey}/members/{uid}` にだけ存在する。**会社をまたぐ権限は存在しない。**
2. `role: 'developer'` は**その workspace 内の全教室**にアクセスできる。`role: 'manager'` は
   `assignedClassroomId` の 1 教室のみ。
3. Auth のアカウント（UID）は全社共通プールだが、**ある会社のサイトで別会社の利用者がログインしても、
   その workspace に `members/{uid}` が無ければ rules と callable の両方で拒否される**。この二重の拒否を
   Phase 0 の rules 越境テストで固定する（§5-4）。
4. 同じ人物が 2 社に関わる場合は、**両方の workspace に member 文書を作る**（UID は同じでよい）。
5. 他社側の開発担当者を `developer` として入れる想定は**無い**（オーナー確定 2026-09-16・計画 §9-7）。
   将来入れる場合も、付与は当該 workspace の member 1 件に限る。

### 1-3. 越境禁止の原則

- **ある会社のビルド・セッション・callable 呼び出しが、別会社の workspace のデータを読む／書くことは一切ない。**
- 実装上の担保は 3 層。どれか 1 つが破れても他で止まることを意図している。
  1. **ビルド固定**: `workspaceKey` は env で焼き込み、UI・URL から選べない。
  2. **rules**: `workspaces/{ws}/**` の read/write は当該 workspace の `members/{uid}` を引いて判定する。
  3. **callable**: 全 callable が引数 `workspaceKey` を受け、`members` を引いて所属を検証する
     （`requireDeveloperMember` / `requireClassroomAccessMember`）。加えて §5-1 の教室存在検査。
- **調査・デバッグでも越境しない。** 他社 workspace のデータは読み取りも必要最小限とし、当該会社の同意の
  範囲内でのみ行う（計画 §8-4）。

### 1-4. 既存 workspace `main` を改名しない

- 既存運営会社の workspaceKey は `main` のまま存置する（オーナー確定 2026-09-16）。改名は Storage パス・
  バックアップ・請求台帳・既に配布済みの QR／共有リンクに波及するため**行わない**。
- 文書・コード・ツールで `main` を「既定値」として暗黙に仮定しない（§6）。`main` は「既存運営会社のキー」
  であって「既定のキー」ではない。

### 1-5. 教室 ID は自動採番のみ（例外 1 件）

- **新しい教室の ID は Firestore の自動採番 ID のみを使う。手入力・意味のある文字列の ID は禁止**
  （オーナー確定 2026-09-16・計画 §10-1）。理由：会社をまたいで同じ ID が並存すると、共有リンク・
  バックアップ・監査で取り違えの芽になる（計画 §6-9）。
- **例外は既存の `test_classroom_20260507_dai`（テスト教室）1 件のみ**。既存のため存置する。
  以後この例外を増やさない。
- 会社が違っても `classroomId` が偶然一致しうる前提で設計する（手入力 ID の既存例があるため）。
  **教室を指すときは常に `(workspaceKey, classroomId)` の組で指す。**

## 2. コア／会社固有の判定基準（計画 §2 の確定）

### 2-1. 判定フロー（この順に問う。1 つでも該当したらコア）

1. **他社の教室データを読める／書ける経路に触るか**（Firestore パス・rules・callable・定期関数・
   バックアップ／復元・トークン発行）→ **コア**。
2. **保存データの形（`AppSnapshotPayload`・`schemaVersion`）を変えるか** → **コア**。
   同じ DB を複数のフロント版が読み書きするため、形の変更はコアが一元管理し後方互換を保証する。
3. **`docs/spec-invariants.md` に載る保証（INV）を触るか** → **コア**。マトリクステストもコアで動かす。
4. **請求の根拠（在籍数台帳・請求月）に触るか** → **コア**。
5. 上のどれにも当たらず、**見え方・言葉・入口の有無・帳票の体裁・追加画面**なら → **会社固有**。

### 2-2. 層と置き場

| 層 | 内容 | 置き場 | 変更者 |
|---|---|---|---|
| **L0 バックエンド** | functions / firestore.rules / storage.rules / indexes / Hosting rewrites の関数指定 | コアリポジトリのみ | コア |
| **L1 ドメイン** | 型・保存／復元・盤面／在庫／日程表の純関数・自動割振・請求計算・機能フラグ基盤 | `src/utils` `src/data` `src/types` `src/integrations` | コア |
| **L2 画面の骨格** | App／盤面／基本データ／日程表 HTML 生成。会社レイヤを**参照する側** | `src/components` `src/App.tsx` `src/utils/scheduleHtml.ts` | コア |
| **L3 会社レイヤ** | ブランド・呼称辞書・機能の既定 ON/OFF・帳票の注記／体裁差・追加画面・`workspaceKey`・Hosting サイト名 | `src/company/`（Phase 1 で新設） | 会社 |

### 2-3. 運用ルール

- 会社固有にできる範囲は **(1) ロゴ・名称・色・呼称 (2) 機能の有無 (3) 帳票の項目追加・注記 (4) 独自の画面・集計**
  の 4 種（オーナー確定 2026-09-16・計画 §10-2）。
- **巨大ファイル（`ScheduleBoardScreen.tsx` / `scheduleHtml.ts`）は分割しない。** 会社差は「差し込み口
  （フック）を数か所開ける」ことで表現する。会社レイヤがコア本体を直接編集し始めた時点で、上流同期の
  衝突と回帰の温床になる（計画 §6-10）。
- 要望が来たら毎回「**差し込み口で足りるか／コアの機能にすべきか**」を §2-1 で判定する。判定結果は
  該当ドメイン正本か本書のどちらかに 1 回だけ記す（重複ゼロ）。

## 3. 本番データ保護ルールの全 workspace 適用

CLAUDE.md の「本番データ保護ルール」は 1 社前提（教室 ID の表が `main` の 5 教室）で書かれている。
これを**全 workspace へ一般化**した規範が以下であり、会社が増えても文言を書き換えずに済む形にする。

1. **Claude（および自動化されたセッション）が Firestore / Storage へ書き込んでよいのは、
   §4 のレジストリに登録された開発用教室・サンドボックス教室のみ**。会社が増えても、その会社の
   レジストリ登録が済むまで**その会社への書き込みは一切できない**（未登録＝書き込み不可が既定）。
2. **登録済み以外のすべての教室は読み取り専用**として扱う。「その会社に開発用教室があるはずだ」という
   推測で書かない（名前・雰囲気で判断しない＝§4 の名前判定廃止と同じ思想）。
3. **他社 workspace は読み取りも必要最小限**。調査は当該会社の同意範囲内で行う（§1-3）。
4. **復元・コピー系の操作は「開いている教室（`actingClassroomId`）」に書き込む**という性質が最も危険で
   あり続ける（2026-06-06 のクロス汚染事故）。実行前に必ず **`(workspaceKey, classroomId)` の両方**を
   確認する。教室名だけの確認は不可。
5. 新しい会社（workspace）の作成は、**安全装置付きの専用コマンドに限定**する（§6-2・Phase 3 T3-1）。
   開発者画面から会社を作れるようにはしない。
6. staging プロジェクト（`komahyouapp-staging`）は**書き込み自由**（本番と分離されたプロジェクト）。
   本規範は本番プロジェクト `komahyouapp-prod` のデータに対する規範である。

## 4. 開発用教室レジストリ（Phase 0 T0-2 の仕様）

### 4-1. As-Is（問題）

- 開発用教室の判定が **(1) 単一 ID 定数 (2) サンドボックス ID 配列 (3) 教室名「開発用教室」の文字一致
  (4) ID に `dev` / `development` を含む曖昧一致** の 4 経路に散っており、**クライアントとサーバーで
  二重実装（手動同期）**されている（計画 §6-2 / §6-3）。
- **名前一致は他社に対して危険**：別の会社が「開発用教室」という名前の教室を作ると、開発用限定機能・
  開発用保存経路・AI 回答が**その会社で誤発火**する。
- **ID の曖昧一致も危険**：会社が増えるほど `dev` を含む ID の偶然一致が起きやすくなる。

### 4-2. To-Be（確定仕様）

1. **開発用教室は `(workspaceKey, classroomId)` の組を明示登録して識別する。** 唯一の権威は
   `src/utils/developmentClassroomRegistry.ts`（新設）。
2. 登録項目は次のとおり。
   - `workspaceKey`（会社のキー）／`classroomId`（Firestore ドキュメント ID・**大文字小文字を区別し完全一致**）／
     `kind`（`'development'` ＝その会社の開発用教室／`'sandbox'` ＝追加の検証用教室）／`label`（人間向けメモ）。
3. **レジストリの不変条件**（テストで固定する）。
   - 同一 `(workspaceKey, classroomId)` の重複が無い。
   - `kind: 'development'` は **workspaceKey ごとに高々 1 件**（＝1 社 1 開発用教室・オーナー確定 2026-09-16）。
   - `classroomId` は空文字でない。
4. **教室名による判定を廃止する。** 「開発用教室」という名前の教室でも、レジストリに未登録なら
   **開発用教室として扱わない**。
5. **ID の曖昧一致（`dev` / `development` の部分一致・`dev_` 前方一致など）を廃止する。** 完全一致のみ。
6. **登録 ID でも `workspaceKey` が違えば false**（会社の壁）。判定関数は必ず workspaceKey を受け取る。
7. **クライアントとサーバーは同一の権威を使う。** サーバー側（`functions/`）はクライアントの権威ファイルを
   `functions/scripts/sync-shared.mjs` で生成複製し、**パリティテストで「同じ入力 → 同じ結果」を固定**する
   （保護者ポータルの `parentSchedule` で確立済みの手法）。手書きの第 2 実装を作らない。
8. **その会社に開発用教室が登録されていない場合の挙動**：
   - 開発用限定機能は **OFF**（安全側）。
   - 開発用教室を必要とするサーバー処理（開発用スナップショット保存など）は
     **`failed-precondition`**（「このワークスペースには開発用教室が登録されていません。」）で明示的に失敗する。
     暗黙に別の教室へフォールバックしない。
9. **staging は当面レジストリに登録しない。** staging の検証用教室（`staging_test_classroom` ほか）は
   `featureRollout` の **`staging-environment` スコープ（プロジェクト ID 判定）** が担う。現に staging には
   「開発用教室」という名前の教室が無く、旧・名前判定は staging で一度も真になっていない（＝この変更で
   staging の挙動は変わらない）。→ 登録の要否は §10-2 の未決事項。
10. **ローカルモード（Firebase 未設定）では `workspaceKey` が空文字になる**ため、レジストリのどの行にも
    一致せず、**開発用教室として扱われない**。旧実装では ID に `dev` を含むローカルのダミー教室が
    開発用教室として振る舞えたが、**この仕様では振る舞わない**（安全側・意図した挙動変更）。
    ローカルでの開発用限定機能の検証方法は §10-3 の未決事項。

### 4-3. この判定が効く範囲（片方だけ有効にしない）

開発用教室の判定は、次の**両方**に使われる。**片方だけ有効／無効にすると 2026-07-09 の QR 混入事故が再発する**
（既存コードのコメントに明記されている意図的なガード。薄めない）。

- **解放側**: 開発用限定機能・他教室バックアップの読み込み（Feature B）・開発用スナップショット保存・
  開発者報告の AI 回答・保護者ポータル（第 1 段）。
- **防御側**: 混入防止ガード（自教室が発行していない提出トークンの QR を出さない／他教室からコピーした
  データのトークンを剥がす）。

## 5. 越境ガード（Phase 0 T0-3 の仕様）

### 5-1. callable の教室存在検査（developer 経路）

1. `requireClassroomAccessMember(uid, workspaceKey, classroomId)` の **developer 経路**に
   「`workspaces/{workspaceKey}/classrooms/{classroomId}` が存在すること」の検査を追加する。
   存在しなければ **`not-found`**（「この教室はこのワークスペースに存在しません。」）。
2. **manager 経路は無改変**。`assignedClassroomId === classroomId` の一致判定により既に workspace 内へ
   束縛されており、読み取りを増やすと全操作のコストと回帰リスクが上がる。
3. **判定は純関数に切り出す**（役割・割当教室・要求教室・教室の存在有無 → 許可／拒否理由）。呼び出し側は
   その結果に従うだけにし、判定の分散（権威の二重化）を作らない。
4. developer 専用で `classroomId` を受ける callable（教室の削除・更新・室長の付け替え・バックアップからの
   ダウンロードなど）は、**既に教室文書を読んで存在確認しているか**を点検し、していなければ同じ検査を足す。
   バックアップ由来のものは「**そのバックアップの中にその教室が含まれるか**」を確認する。
5. この検査が守る保証：**開発者の端末・ツールが誤って別会社の教室 ID を渡しても、その会社の workspace に
   存在しない限り操作は成立しない**（2026-06-06 型の取り違え事故に対する最後の砦）。

### 5-2. 何を守らないか（明示）

- この検査は「**別会社の workspaceKey を渡した場合**」を守るものではない。それは `members` 検査（§1-3）が
  既に止めている。守るのは「**正しい workspaceKey ＋ 別会社（または存在しない）教室 ID**」の組み合わせ。

### 5-3. トップレベル公開文書への `workspaceKey` 付与

1. `boardShares/{token}`（講師日程共有）に **`workspaceKey` を書き足す**（発行時のみ）。
2. **読み取り側は無改変**とする。既存の共有リンク（`workspaceKey` を持たない文書）を壊さないため、
   読み取りでの必須化・照合は**行わない**（後方互換）。
3. 目的は**監査・削除・オフボーディング時に「どの会社の共有か」が分かること**。越境の実害を今すぐ塞ぐ
   ものではない（教室 ID は自動採番で実質一意・§1-5）。
4. 同様に、今後トップレベルへ文書を作る機能は**発行時に `workspaceKey` を書く**ことを既定とする（§1-1-2）。

### 5-4. rules 越境テストの保証内容

## 6. 運用ツールの棟指定必須（Phase 0 T0-4 の仕様）

### 6-1. `--workspace` の必須化

1. `tools/*.mjs` のうち Firestore / Storage を参照するものは、**`--workspace <key>` を必須引数**とする。
   未指定なら使い方を表示して異常終了する。**`'main'` の既定値を廃止**する。
2. 理由：既定値があると、会社が増えたときに**「何も指定しなければ既存運営会社を触る」**という事故の形が
   残る。コマンド履歴・runbook のコピペが最も起きやすい経路であり、既定値の廃止が最小コストの対策。
3. `copy-prod-classroom-to-staging.mjs` は**既定教室（日大前）も廃止**し `--classroom <id>` を必須にする
   （本番教室 ID を既定値としてリポジトリに置かない・計画 §6-12）。
4. `--project`（本番／staging の選択）の既定値は**据え置き**。プロジェクトの取り違えは URL・出力で気づける
   のに対し、workspace の取り違えは静かに成功してしまうため、危険度が異なる。
5. env（`VITE_FIREBASE_WORKSPACE_KEY`）から workspace を読む既存経路は残してよい。**削るのは「env も引数も
   無いときに `'main'` を使う」フォールバックだけ**。
6. 引数解析は**テスト可能な純関数**として切り出し、各ツールで「`--workspace` 無し → エラー／有り → 反映」を
   ユニットテストで固定する。
7. 呼び出し側（GitHub Actions のワークフロー入力・`docs/runbooks/*`・`docs/*`・`CLAUDE.md`・
   `.claude/skills/**` のコマンド例）も**同時に追随**させる。片方だけ変えると手順書どおりに実行して失敗する。

### 6-2. 会社（workspace）の新設

- 新しい会社の作成は **安全装置付きの専用コマンドに限定**する（開発者画面からは作らない・オーナー確定
  2026-09-16）。**指定した新キー以外へ書けないガード**（既存キーの指定は拒否）を必須とする。
  実装は Phase 3（T3-1）。

## 10. 未決事項（オーナー確認・別タスク）

### 10-1. 規約上プロジェクト分離を要求する会社が出た場合の扱い（計画 §9-8・未回答）

- 現状の設計は「**1 Firebase プロジェクト＋会社＝workspace**」。規約・監査要件で**プロジェクト分離**を
  求める会社が現れた場合のみ、例外として別プロジェクトを立てる（コアは env でプロジェクトを切り替えられる
  ことを staging で実証済み）。
- **未決**: 例外を認めるか／認める場合の追加コスト（functions・rules・indexes・Scheduler・監視・staging を
  N 回デプロイ。一括請求は各プロジェクトの台帳を突合する別ツールが必要）をどう扱うか。
- **暫定の扱い**: 「**該当する会社が出たときに判断する**」（オーナー回答どおり）。Phase 0〜3 の設計はこの
  例外を前提にしない。

### 10-2. staging の検証用教室をレジストリに登録するか

- 現状（§4-2-9）：**登録しない**。staging 向けの機能解放は `staging-environment` スコープ
  （プロジェクト ID 判定）が担い、レジストリは本番プロジェクトの会社別開発用教室だけを持つ。
- **論点**: staging の教室で「開発用教室限定の機能」を検証したい場面が出たとき、
  (a) レジストリに staging の workspaceKey ＋ 教室 ID を足す／(b) `staging-environment` スコープを使う／
  (c) 判定を「レジストリ **または** staging プロジェクト」にする、のいずれを採るか。
- **暫定**: (b)。staging では**プロジェクト全体が検証環境**なので教室単位の区別に意味が薄い、という理由。
  ただし「開発用教室**だけ** ON」の機能を staging で試したい要望が出たら再検討する。

### 10-3. ローカルモード（Firebase 未設定）での開発用限定機能の検証方法

- §4-2-10 のとおり、ローカルモードでは `workspaceKey` が空文字になり、**開発用教室として判定されない**
  （旧実装では ID に `dev` を含むダミー教室が開発用教室として振る舞えた）。
- **論点**: ローカルで開発用限定機能を触りたい場合、
  (a) `.env.local` に `VITE_FIREBASE_WORKSPACE_KEY=main` と開発用教室 ID を設定して確認する／
  (b) レジストリにローカル用の行（`workspaceKey: ''` など）を足す／
  (c) ローカルでの確認は諦め、staging または開発用教室（実 Firebase）で確認する、のいずれを採るか。
- **暫定**: (c)。レジストリに「空キー」の行を足すと、**空キーで通る穴**を作ることになり §4 の趣旨（未登録は
  常に false）に反するため。開発中に不便が出たら (a) を手順化する。
- **影響の確認が必要**: この挙動変更でローカル開発の手順が変わる箇所（`docs/`・skills の記述）が無いか、
  T0-2 の実装時に `grep` で点検する。

### 10-5. CLAUDE.md の本番データ保護ルールの書き換え時期
