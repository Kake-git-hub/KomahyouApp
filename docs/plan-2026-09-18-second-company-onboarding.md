## 0. 結論（先に要点）

**目的**: 2 社目は未定だが、**決まった日から数日で本番導入できる状態**を先に作っておく。

**方針（3 行）**

1. **フォークは切らない。** コアリポジトリ 1 本のまま、会社ごとの「プロファイル」と「ビルド（env）」を分けて配信する。
   要望はまず差し込み口（Phase 1 のフック）で吸収し、フォーク（上位計画 §9-1 方式 B）は「差し込み口で足りない要望が
   恒常化した」ときの最後の手段にする。
2. **事前準備（§3）は 2 社目が決まる前に全部済ませ、staging で 1 回「架空の会社」を通しで導入して手順を確定する。**
   本番でやるのは §4 の当日手順だけにする。
3. **既存運営会社は株式会社アーチ（`workspaces/main`）**。会社名はプロファイルと棟の文書に持ち、workspaceKey は
   `main` のまま（改名しない・上位計画 §9-2）。

**事前準備の合計目安**: 約 7 人日（§3 の表・請求 P-11 を含む）。当日手順は約 2 時間（§4）＋ 会社側のデータ準備。

## 2. オーナーの判断点（回答欄・推奨を先頭に）

### D-1 ★ 薬円台校の運営会社

- オーナー情報（2026-09-18）: 緑が丘校・日大前校は**株式会社アーチ**が運営。**薬円台校の運営会社は未確認**。
- 論点: `workspaces/main` に 3 教室が同居している。薬円台校が別会社なら「1 workspace ＝ 1 会社」（spec §1）に
  反する状態が既にある。
- 推奨: **(a) 薬円台校もアーチ（または同一グループの請求先）なら現状維持**。
  (b) 別会社なら、**当面は `main` に同居のまま**（請求は教室宛で分ける）とし、会社宛合算請求（T3-3）を入れる時点で
  薬円台校を別 workspace へ移すかを再判断する（教室の workspace 間移動は QR・共有リンク・バックアップに波及するため
  軽くない。spec §1-4 と同じ理由）。
- [x] **回答（2026-09-18）: 薬円台校はテスト用で、もう使っていない。削除してよい。**
  → 削除は本番 Firestore への書き込みなので **Claude は行わない**（CLAUDE.md 本番データ保護ルール）。
  オーナーが開発者画面の「教室を削除」（`deleteClassroom`・パスワード再認証つき）で行う。削除前に開発者バックアップ
  （JSON 書き出し）を 1 回取る。削除後は CLAUDE.md の教室一覧・`docs/spec-multi-tenant.md` §8-1・
  `firebase/rules/firestore.rules.test.ts` 等に残る「本番 3 教室」の記述を「本番 2 教室」へ直す（P-0）。
  これで `workspaces/main` ＝ 株式会社アーチ 1 社に揃う。

### D-2 会社キー（workspaceKey）の命名規則

- 推奨: **英小文字と数字だけ・3〜16 文字・会社名のローマ字略**（例 `arch`＝既存は `main` で固定、2 社目は `xyz`）。
  URL（`komahyou-<会社>.web.app`）・Storage パス・プロファイルのファイル名に同じ文字列を使う。
- [x] **回答（2026-09-18）: 会社キーは会社登録時に開発者（オーナー）が入力する。**
  → 自動生成や事前の一覧管理はしない。入力値は上の規則（英小文字と数字・3〜16 文字・`main` と登録済みキーは拒否）で
  検証し、通らなければ登録を止める。**登録の入口は spec §6-2 の確定どおり安全装置付きの専用コマンド**
  （`tools/provision-workspace.mjs`）で、キーはその引数として開発者が入力する。開発者画面からは作らない
  （§6-2・2026-09-16 確定）。画面から登録したい場合は仕様変更になるので別途相談（§2-A 確認 3）。

### D-3 会社サイト名（URL）

- 推奨: **`komahyou-<会社キー>.web.app`**（上位計画 §9-3 確定）。既存の `komahyouapp-prod.web.app` はアーチ用のまま
  （配布済み QR を変えない）。独自ドメインは会社の要望があったときだけ。
- [x] **回答（2026-09-18）: 推奨のとおり**（`komahyou-<会社キー>.web.app`・既存 URL は不変）。

### D-4 2 社目の開発用教室

- 推奨: **会社ごとに 1 教室**を「開発用」として本番 workspace 内に作り、台帳へ登録（spec §4-2-3・§7-14）。
  2 社目の確認リストや先行機能はその教室で検証する。テスト教室（sandbox）は作らない。
- [x] **回答（2026-09-18）: 後回しにせず導入時に用意する**（会社ごとに 1 教室を開発用として台帳に登録）。

### D-5 請求（T3-3）を導入前にやるか後にやるか

- 推奨: **後**。導入初月〜数か月は、開発者画面の既存の教室別請求（`main` と同じ画面を 2 社目のサイトで開く）で
  会社ごとに出し、会社宛合算・全社一覧・許可者の member 化は 2 社目の運用が落ち着いてから入れる。
  理由: 請求は本番データ保護ルールの対象で、導入当日に新しい経路を同時に動かすと切り分けが難しい。
- [x] **回答（2026-09-18）: 後回しにせず導入前に用意する**（会社宛合算請求・全社一覧・許可者の member 化・
  会社標準単価＋教室上書き＝上位計画 T3-3）。→ §3 の P-11 として事前準備に組み込む。
  請求画面は開発者専用なので室長の操作には影響しない（§2-A 影響 3）。

### D-6 既存プロファイルの表示名

- 現在 `displayName: 'スクールIE'`。**`株式会社アーチ`** に直し、ブランド名（スクールIE）は別項目にするか。
  Phase 1 ではどちらも画面に出さない（帳票の校舎名欄は利用者入力）ので、どちらでも挙動は変わらない。
- 推奨: `displayName` を会社名（株式会社アーチ）、`brandName`（新設）をブランド（スクールIE）に分ける。
- [x] **回答（2026-09-18）: 既存利用者に影響が無いなら、会社名を「株式会社アーチ」にしブランド名（スクールIE）を分ける。**
  → 影響なし（どちらも Phase 1 では画面・帳票・請求書に出ない。`profile.test.ts` で「出力不変」を固定したまま
  `displayName: '株式会社アーチ'`・`brandName: 'スクールIE'`（新設）にする）。P-1 に含める。

### D-7 `index.html` の `<title>` の扱い（spec §11-1 の宿題）

- 推奨: **vite の HTML 変換で `appName` を注入**し、`index.html` はコアのまま。フォークを切らない方針なら
  会社ごとのビルドで自動的に変わる。
- [x] **回答（2026-09-18・確定）: タブ名は「コマ表アプリ_緑が丘校」の形（`<アプリ名>_<教室名>`）。**
  → 既存利用者に見える変更（「緑が丘校 | コマ表アプリ」→「コマ表アプリ_緑が丘校」）。§2-A 確認 1 で承認済み。
  教室名が無い場面はアプリ名だけ（ログイン前「コマ表アプリ」）、開発者画面は「コマ表アプリ_開発者画面」に揃える。
  `index.html` の静的 `<title>` はアプリ名のまま（ロード中の一瞬だけ）でよく、フォークを切らないので
  §11-1 の宿題は「静的タイトルはコアの値で固定・実行時に `<アプリ名>_<教室名>` へ差し替え」で閉じる。

## 5. 導入後、要望が出たときの手順（2026-09-18 の方針を正式化）

1. **受付**: 報告・要望は triage で GitHub Issue 化（ラベル `company:<キー>` を新設）。利用者報告由来（`source:user-report`）
   はオーナー確認まで着手しない（CLAUDE.md）。
2. **判定（spec §2-1）**: 「他社のデータに触れるか」「INV に載る保証に触れるか」「全社に役立つか」のどれかなら**コアの機能**。
   コア機能は機能フラグ（基本スコープ＋会社既定）で出し分け、開発用教室 → staging → 会社の開発用教室 → 会社の全教室の順で昇格。
3. **会社固有で差し込み口に収まる**（呼称・帳票の注記／ヘッダ・追加ボタン／メニュー・機能の会社既定・ブランド）:
   その会社の `src/company/profiles/<キー>.ts` だけを変える。コア本体は触らない。アーチのビルド出力不変をテストで確認。
4. **会社固有で差し込み口に収まらない**: **先にコアへ差し込み口を 1 つ増やす**（既定は空・出力不変・テスト同梱・spec §11 に追記）。
   その上でプロファイル側に実装する。差し込み口の増設は spec-curator が §2-2 の層に照らして承認する。
5. **ユーザビリティに影響する要望**は、着手前に懸案と妥協案をオーナーへ提示して落とし所を決める（CLAUDE.md 標準フロー 2）。
6. **記録**: CHANGELOG に `company:<キー>` を添える。会社固有の変更でも INV 台帳の保証（盤面・在庫・日程表）に触れる場合は
   INV 完了定義 4 点を満たす。

## 6. フォーク（方式 B）へ切り替える判断基準

次のいずれかが続いたら、その会社だけフォークを切る（上位計画 §9-1・§7 Phase 2 T2-2〜T2-4 を起動）。

- 差し込み口を **3 つ以上**増やしても、その会社の要望が収まらない。
- 会社固有の**画面が複数本**になり、コアの盤面ロジック・保存経路の内部に依存し始めた。
- 会社側が**自分たちの開発担当**でコードを触りたいと言った（コアの履歴を見せない私有フォークにする・上位計画 §10-4）。
- 規約上 **Firebase プロジェクトの分離**を求められた（spec §10-1・例外扱い）。

切り替え前に済ませること: フォーク用 CI 雛形（T2-2）・`upstream-sync` スキル（T2-3）・触ってよいパスの CI ガード（T2-4）・
会社版番号 `コア版+会社識別子`（spec §7-7）。
