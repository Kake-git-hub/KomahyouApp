  `src/components/parent-portal/ParentPortalPage.tsx`（公開ページ）/ `functions/src/parentPortal.ts`（`parentPortalApi`・
  `issueStudentPortalToken` / `revokeStudentPortalToken` / `markParentMessagesNotified`）/ `firebase/firestore.rules` /
  `firebase.json`（rewrite）。段階計画は `docs/plan-2026-09-11-five-requests.md` §7-6（K-1〜K-6）。

### 0-4. 開発用教室の確認リストを受けた改定（2026-09-14・第6版 k-4 / k-5 の要改善）

オーナーの確認結果と回答で次の 4 点を確定した（**§C・§D の本文より、この節が優先**）。

1. **表示期間は暦の 1 か月単位**。移動も 1 か月単位（「前の月」「次の月」）で、動かせるのは**先月・今月・来月**だけ。
   見出しは「2026年9月」。サーバー `resolveParentScheduleRange` が月に丸め、`bounds` は先月 1 日〜来月末日。
2. **行を出すのは授業（通常・振替・増コマ・お休み・出席済み）がある日だけ**。授業の無い日、`templateFreezeBeforeDate`
   より前でデータの無い日、**毎週の定休曜日（`closedWeekdays`）は行を出さない**。
3. **教室休みは臨時・祝日休み（`holidayDates`。`forceOpenDates` で開けた日は除く）だけ「教室休み」の 1 行を出す**
   （オーナー回答: 定休曜日まで出すと一覧が休みの行で埋まるため）。
4. **講習期間という区別をやめる**。講習期間中の日も通常日と同じ「休講 → 盤面優先 → テンプレ補完」で**通常授業だけ**を出す。
   講習コマ（`special`）は従来どおり出さない。講習の予定は**講習提出QR（生徒日程表のQR）で確認する形式**（オーナー回答）。
   応答から `kind: 'lecture-period' / 'none'` と `lectureLabel` を削除した（`kind` は `closed / board / template`）。
5. **講習だけの月の注記**（2026-09-14 確認リスト k-4 再報告・オーナー回答）。講習だけだった月（例: 夏期講習中に入塾した生徒の 8 月）は
   臨時休みの行しか残らず「出席データが出ない」ように見える。講習コマは引き続き出さず、応答に真偽値 `hasLectureLessons`
   （範囲内の開講日に、この生徒の講習コマ＝配置 or 出欠記録（`moved` 除く）が盤面にあったか。件数・日付は出さない）を足す。
   画面は**通常授業の日が 1 日も無く `hasLectureLessons` が真**のときだけ
   「この月は通常授業がありません（講習の日程はこのページには表示されません）。」を出す。
   講習も無い月は従来どおり（行が 0 件なら「この月の授業の予定はありません。」、臨時休みの行だけなら何も出さない）。
   印の無い旧 functions の応答は偽として扱う（Hosting が先に出ても壊れない）。

### 0-3. デプロイ順の注意（2026-09-13 に実際に踏んだ）

`firebase.json` の rewrite が**まだ存在しない関数**を指していると、Hosting のデプロイが
`Cloud Run service "parentportalapi" does not exist in region "asia-northeast1"` で **400 になって失敗する**。
main へのマージは Hosting と Cloud Functions のワークフローを**並行**で起こし順序保証が無いため、
新しい rewrite を追加した回は Hosting が先に走ると必ずこれで落ちる（本番は旧版のまま無傷＝fail-closed）。

- 対処: **Cloud Functions のデプロイが緑になってから Hosting を再実行**する（Actions → Deploy to Firebase Hosting → Re-run）。
- 実反映の確認: `GET https://komahyouapp-prod.web.app/api/parent/xxxxxxxxxxxxxxxx` が `410`＋
  「このリンクは現在ご利用いただけません。」の JSON を返すこと（409 誤成功対策として関数の live 応答で確かめる）。
- Firestore ルールは main マージでは反映されないので `firebase deploy --only firestore:rules` を別途実行する
  （未反映だと `parentMessages` の購読が permission-denied になり、室長に連絡が届かない）。

## A. 目的と範囲

- 目的: 生徒ごとの固定QRから、保護者が **(a) 通常授業＋振替の予定を確認** し、**(b) 室長へテキストで連絡** できる。
- **オーナー確定（2026-09-11・変更不可）**:
  1. 表示範囲は **通常授業＋振替**（休んだコマは振替先まで示す）。
  2. 連絡は **アプリ内通知のみ**（保護者への自動メール／LINE 送信はしない）。
  3. 返信は **一方向（保護者 → 室長）**。ポータルから室長の返信は読めない。
  4. QR の配布形は **基本データ画面の生徒ごとに表示・印刷**。
- 非目的（この仕様では扱わない）:
  - 保護者アカウント・ログイン・パスワード（ベアラートークン 1 本で完結させる）。
  - 双方向チャット・保護者側での既読表示・添付ファイル。
  - 欠席連絡の自動反映（連絡は**テキストが室長に届くだけ**。盤面・在庫・出欠・提出は一切変化しない）。
  - 講習の希望提出（既存の `lectureSubmissionApi` / `/s/{token}` の担当。§J-1）。
  - 請求・料金・成績の表示。
- 対象: 在籍中の生徒 1 名につき 1 リンク（保護者用）。講師・外部関係者向けのリンクは作らない。

## B. トークン

### B-1. 権威と写し

- **権威** = Firestore `studentPortalTokens/{token}`（トップレベル。`lectureSubmissions/{token}` と同じ並び）。

  | フィールド | 型 | 内容 |
  |---|---|---|
  | `workspaceKey` | string | 発行時の workspace（既定 `main`） |
  | `classroomId` | string | **発行元教室**。参照の権威（doc 側を信じる。§G-2） |
  | `studentId` | string | `StudentRow.id` |
  | `createdAt` | ISO8601 | 発行時刻（サーバー時刻） |
  | `createdByUid` | string | 発行した室長の UID（サーバーが付ける。自己申告にしない） |
  | `revokedAt` | ISO8601 / null | 失効時刻。null 以外なら常に拒否 |
  | `revokedReason` | string | `reissue` / `manual` / `studentDeleted` のいずれか |

- **写し** = `StudentRow.parentPortalToken`（QR 描画用）と `StudentRow.parentPortalTokenClassroomId`（発行元教室タグ）。
  写しは表示のためだけに存在し、**検証には使わない**（検証は必ず権威 doc を読む）。
- Firestore ルール: `studentPortalTokens` は **クライアントから read も write も不可**（`allow read, write: if false`）。
  読み書きは Cloud Functions の Admin SDK のみ。`boardShares` のような公開 read 文書は**作らない**（§J-2）。
- トークン文字列: `A-Za-z0-9_-` の **32 文字**（暗号論的乱数）。`/s/{token}`（16〜64 文字）と文字集合は同じだが、
  URL のプレフィックスで用途を分ける（`/p/` = 保護者ポータル、`/s/` = 講習提出）。

### B-2. 発行・再発行・失効

- 発行は callable `issueStudentPortalToken({ classroomId, studentId, reissue })`。呼べるのは**その教室のメンバー（室長）**のみ
  （保存と同じ `requireClassroomAccessMember`）＋**サーバー側でもフラグを確認**する（§0-2）。
- **生徒 1 名につき有効トークンは常に 1 本**。有効トークンがある状態で発行を呼ぶと、旧トークンを
  `revokedAt`（`revokedReason='reissue'`）にしてから新規発行する（＝「再発行」）。
- 発行のきっかけは**基本データ画面の「QR」ボタンの初回押下**（getOrIssue で冪等・§0-2。生徒追加時の自動発行はしない）。
- `revokeStudentPortalToken({ classroomId, studentId, reason })` で明示失効（§0-2。`reason` は `manual` / `studentDeleted`）。失効は不可逆
  （復活させない。必要なら再発行して配り直す）。
- **生徒を名簿から削除**したときは、その生徒の有効トークンを `revokedReason='studentDeleted'` で失効させる
  （`spec-basic-data.md` の削除確認モーダルと同じ導線で実行）。
  ※2026-09-13 に在籍一覧の生徒削除は「退塾」ボタン（退塾日の記録・行は残す）へ置き換わった。退塾では失効を呼ばない
  （P-6 の在籍判定で退塾日当日から 410。退塾日を消せば同じQRが再び使える）。「削除」は非在籍一覧にだけ残り、行は残して
  `deletedAt` を記録する（アプリ上から消す）。このときに `studentDeleted` で失効させる。

### B-3. 他教室コピー時の剥がし（本番データ保護）

- 教室コピー・バックアップ復元で `StudentRow` が別教室へ渡ると写しのトークンが残り、**開発用教室の画面に
  本番生徒のQRが出る**（開いた保護者に本番教室の日程が見える）。講習提出トークンで実際に起きた事故
  （`b2e2048` / v1.5.415）と同型なので、同じ対策を必ず踏襲する。
- 除去は**二層**（§0-2）: ①教室コピー時の無条件 strip（`buildDevelopmentClassroomCopyPayload`）②表示時の発行元一致ガード
  （`isParentPortalTokenOwnedByClassroom` → 一致しなければサーバーへ getOrIssue）。`stripForeignParentPortalToken*` は
  ②の代替として用意してあるが**現在は呼んでいない**（クライアントはトークン文書に書かないため、表示時の判定で足りる）。
- 剥がしの**唯一の権威関数**を新設する（`src/utils/developmentClassroom.ts` に同居）:
  - `stripParentPortalToken(row)` … `parentPortalToken` と `parentPortalTokenClassroomId` を無条件に落とす（純関数）。
  - `stripForeignParentPortalToken(row, classroomId)` … `parentPortalTokenClassroomId !== classroomId` のときだけ落とす。
  - `StudentRow[]`（配列）単位のラッパを用意する。既存の `stripSubmissionToken*` は `studentInputs`（Record）が対象で
    **形が違う**ため、流用せず別関数にする。除去するフィールドの定義は 1 か所に集約し、分散させない。
- 適用箇所は既存の提出トークン剥がしと**同じ呼び出し点**（教室コピー／バックアップ読込／開発用教室での外来トークン除去）。
  片方だけに足さない（非対称が回帰源）。

## C. 公開ページ `/p/{token}`

- ルーティングは `src/main.tsx` に追加する。`/p/{token}`（本番・短縮）と `#/parent/{token}`（ローカル開発）。
  **App 本体を読み込まない軽量経路**（`/s/{token}` と同じ扱い。Firebase 認証も Firestore 直読みも行わない）。
- Hosting rewrite は `firebase.json` に `/api/parent/**` → `parentPortalApi`（asia-northeast1）を追加する。
  ページ自体は `**` → `/index.html` の既定 rewrite で配信される。
- スマホ縦持ち前提。**`applySubmissionViewport()` は呼ばない**（§0-2）。`width=device-width` のまま通常のモバイル CSS で組む。
- **表示する情報**:
  - 生徒の表示名（`displayName`。無ければ `name`）／教室名／データの基準時刻（§D-6）。
  - 期間内の日付ごとの行: 日付・曜日・時限・時刻（`slotTimes`）・科目。振替で入ったコマは「振替」と明記。
  - 休んだコマ: 「お休み」＋振替先が決まっていれば「振替: ○月○日 ○限」、未定なら「振替日は調整中です」。
  - 講習期間に入る日: 「講習期間（別途ご案内）」の 1 行のみ（個別の予定は出さない。§D-4）。
  - 注記 3 種（常時表示）: ①「教室で**保存された時点**の予定です」／②「予定は変更になることがあります」／
    ③「変更・欠席のご連絡はこのページ下部からお送りください（お電話でも受け付けます）」。
  - 下部に「教室へ連絡」フォーム（§E）。
- **表示しない情報（載せない）**:
  - 講師名（P-2）・他の生徒の名前・机番号・座席配置・出席人数。
  - 残コマ数／未消化ストック／講習の希望科目数／料金・請求。
  - メールアドレス・生年月日・入退塾日・内部 ID（`studentId` を本文にも DOM にも出さない）。
  - 他日を含む教室全体の予定（＝盤面そのもの）。
- HTTP キャッシュ: API 応答は `Cache-Control: no-store`（古い日程を見せない）。

## D. 日程計算の規則

権威は純関数 **`buildParentScheduleView(payload, studentId, fromDate, toDate)`**（`src/utils/parentSchedule.ts`）。
クライアントと Cloud Functions の**二重実装を禁止**し、functions 側はビルド時に同梱する
（`functions/src/generated/` へ複製を生成。手書きコピーの持ち込み禁止。同じ fixture で両側からテストする）。

### D-1. 入力

> **2026-09-14 改定（§0-4）**: 期間は暦の 1 か月単位（先月〜来月）。下の「既定 −7〜+28 日／丸めの確定挙動」は旧仕様。

- `payload` = 教室スナップショット（`readStoredSnapshotPayload` が返す gzip 解凍済み JSON）。
  参照するのは `weeks`（保存済み盤面）・`templateCells`（通常授業テンプレ）・`specialSessions`（講習期間）・
  `availability`（`closedWeekdays` / `holidayDates` / `forceOpenDates`）・`slotTimes`・`students`。
- `fromDate` / `toDate` は JST の `YYYY-MM-DD`。既定と上限は §0 P-1（既定 −7〜+28 日、上限 −56〜+84 日）。
  上限を超える範囲を要求されたら上限へ丸める（エラーにしない）。**丸めの確定挙動**（`resolveParentScheduleRange`）:
  片方だけ指定された要求は既定と同じ 36 日幅で反対側を補う／限界外は限界へ丸める／`to < from` は `to = from`（1 日）／
  42 日を超える幅は `to` を切り詰める／解釈できない文字列は無視して既定に戻す。

### D-2. 日ごとの決定順（この順序を変えない）

> **2026-09-14 改定（§0-4）**: 2（講習期間判定）は廃止し「休講 → 盤面優先 → テンプレ補完」とする。休講日は臨時・祝日休み（`holidayDates`）だけ「教室休み」の 1 行を出し、定休曜日と授業 0 件の日は行を出さない。

1. **休講日判定**: `holidayDates` に含まれる、または `closedWeekdays` の曜日で `forceOpenDates` に無い日は
   「お休み（教室休講）」として授業行を出さない。**休講日の盤面セルに手動配置があっても出さない**
   （判定順序を曲げないため。`forceOpenDates` の日は通常どおり出る）。
2. **講習期間判定**: `specialSessions` のいずれかの `startDate ≤ 日付 ≤ endDate` なら「講習期間（別途ご案内）」で確定し、
   以降の抽出を行わない（§D-4）。
3. **盤面優先**: `weeks` にその日付のセルがあれば、**盤面の内容だけ**を使う（テンプレ展開で足さない）。
   盤面にその日があって生徒の配置が 1 件も無ければ「授業の予定はありません」が正（テンプレで補わない）。
4. **テンプレ補完**: `weeks` にその日付のセルが無い日だけ `templateCells` を曜日展開して**通常授業のみ**を出し、
   その行に「予定（変更の可能性あり）」を付ける。展開の条件は盤面と同じ
   （在籍期間内＝`isActiveOnDate` 真／`templateFreezeBeforeDate` より前の日付は展開しない）。

### D-3. 盤面から拾う対象

| 種別 | 判定 | 保護者ページでの表示 |
|---|---|---|
| 通常授業 | `lessonType === 'regular'` | 科目のみ（種別ラベルなし） |
| 振替 | `lessonType === 'makeup'` | 「振替」 |
| 増コマ | `lessonType === 'extra'` | 科目のみ（P-9） |
| 講習 | `lessonType === 'special'` | **出さない**（通常は §D-4 で日ごと除外される。期間外に置かれた講習コマも出さない） |
| 欠席 | `statusSlots` の `status === 'absent'` | 「お休み」＋振替先（§D-5） |
| 振替なし欠席 | `status === 'absent-no-makeup'` | 「お休み」＋「振替なし」（振替コマなら「9/19 2限分 振替なし」・2026-09-14 k-11 で 1 行化） |
| 出席済み | `status === 'attended'` | その日に授業があった扱いで表示（過去日） |
| 移動済み | `status === 'moved'` | **行としては出さない**（移動先が別に出る＝二重表示の防止）。ただし移動先が別の日の振替なら、振替元の日に「お休み＋振替先」を補う（§D-5・k-11） |

- 生徒の同一性は `managedStudentId` を最優先し、無い場合のみ表示名で照合する（在庫キーの規約と同じ）。
  `managedStudentId` があるのに名前一致で拾う実装にはしない（同名別人の混同防止）。

### D-4. 講習期間の除外

> **2026-09-14 改定（§0-4）で廃止**: 講習期間中も通常授業を出す（講習コマは出さない）。以下は旧仕様の記録。

- **判定は日付単位**。`specialSessions[].startDate ≤ 日付 ≤ endDate`（両端含む）に入る日は、通常授業・振替を含め
  **その日の予定を一切表示しない**（P-8）。表示は「講習期間（別途ご案内）」の 1 行。
- 複数の講習期間は日付範囲が重複しない制約がある（`spec-special-session-submission.md` §A の重複禁止）ため、
  「どの講習か」の曖昧さは生じない。講習名は表示してよい（例:「冬期講習（別途ご案内）」）。
- 講習期間が表示範囲を跨ぐ場合は、跨いだ日だけが除外される（期間の一部が範囲内でも、範囲内の期間外の日は通常どおり表示）。

### D-5. 休み → 振替先の解決

- 起点は「その生徒のその日の `absent`（欠席）」。振替先は、表示期間の**内外を問わず** payload 全体の `weeks` から
  「同一生徒・同一科目・`makeupSourceDate` がその欠席日」のコマを探して示す
  （`buildLinkedLessonDestinationMap` と同じ鍵の作り方: 在庫種別・生徒キー・科目・振替元日付・振替元限）。
- **振替先のコマが出席済み（`attended`）になっていてもリンクを切らない**（P-10）。盤面側 `lessonLinks` は
  `absent` のみを起点にするため「出席にしたら振替日が消えた」という表示バグが起きた（2026-09-04 緑が丘報告）。
  保護者ページは `statusSlots` の `attended` も走査対象に含める。
- 振替先が見つからないときは「振替日は調整中」。**在庫数・未消化数は出さない**。
- 振替先が `toDate` より先でも日付として示す（表示範囲外でも保護者には重要な情報）。
- **振替先 → 振替元も示す**（2026-09-14 オーナー指示・確認リスト第9版 k-11）: 振替コマ（配置の `makeup`、および振替を
  `attended` / `absent-no-makeup` にした `statusSlots` の `lessonType==='makeup'`）には `makeupOrigin`
  （`makeupSourceDate` と `makeupSourceLabel` の「◯限」）を付け、「振替（振替元: 9月15日 4限）」と出す。
  元コマが読めなければ日付だけ。振替元が同じ日なら付けない。
- **振替元の日に「お休み＋振替先」を補う**（2026-09-14 確認リスト第9版 k-11「休みとなった日が行表示されない」）:
  丸ごと振替は振替元の机を空にするだけ、生徒のドラッグ移動は振替元に `moved`（非表示）を残すだけで、振替元に `absent` が無い。
  そこで振替先（上の振替コマ）の `makeupSourceDate`＋`makeupSourceLabel` の限から逆に引き、振替元の日に `kind:'absent'`＋
  `makeupDestination` を補う（`buildMakeupOriginLinksByDate` / `appendMakeupOriginAbsences`）。
  - 同じ限・同じ科目の行が既にあれば足さない（`absent` で振替先が引けていなければ埋める・通常/出席があればそのまま）。
  - 振替コマ自体を休みにした `absent`（在庫へ戻った）からは補わない。元コマ（限）が読めない振替からも補わない。
  - 振替元が臨時・祝日休み（`holidayDates`）なら、「教室休み」の行に `makeupDestinations`（振替先一覧）を添える。
  - 生徒の同一性は §D-3 と同じ matcher（本人の振替だけ）。振替先は全週から引く（表示範囲外でも出る）。
- **表記は 1 行に収まる短い形**（k-11「振替日付も含めて1行表示」）: 休み「9/30 5限に振替」／振替「9/23 5限の振替」／
  振替を出席「出席（9/23 5限の振替）」／振無休「9/19 2限分 振替なし」／教室休み「9/28 3限に振替」。月日は「M/D」。
  幅 390px で全行 1 行（360px では「今日」印の付く行だけ折り返すことがある）。
- **一覧は 1 コマ 1 行**（2026-09-14 オーナー指示・k-10）: 日付は同じ日の先頭行だけ（「14日(月)」・月は見出し）、
  時限と開始時刻、科目＋補足を 1 行に並べる。教室休み・授業の無い日は 1 行。テンプレ由来は行末の「予定」印＋一覧上の説明 1 行。

### D-6. 「保存済みの状態」の明示

- API が読むのは**サーバーに保存されたスナップショット**。室長の端末で編集中・未保存の変更は反映されない。
- 応答に `snapshotSavedAt`（最終保存時刻）を含め、ページ上部に「◯月◯日 ◯時◯分 時点」と表示する。
- `weeks` は端末側で先の週を生成するため、サーバーに無い未来週が存在しうる。§D-2 の 4 が働いた日には
  「予定（変更の可能性あり）」を必ず付け、テンプレ由来であることを保護者に示す。

## E. 室長への連絡

### E-1. 送信（POST `/api/parent/{token}`・§0-2 で GET と同じ URL に統一）

- 入力: `token` / `body` / `senderName`（任意）。
- 検証（すべてサーバー側。クライアント検証は UX 補助であって権威ではない）:
  - トークンが有効（§G-2 の 5 段検証をすべて通る）。
  - `body` は制御文字（改行・タブ以外）を除去したうえで **1〜500 字**。0 字は 400、501 字以上も 400。
  - `senderName` は 0〜30 字。超過は 400。
  - 回数制限: **トークンあたり 1 日 5 件**（JST 0:00 リセット）／教室あたり 1 時間 60 件／全体 1 分 30 件。
    超過は **429** と「本日の送信上限に達しました。お急ぎの場合は教室へお電話ください」。
- 保存先: `workspaces/{ws}/classroomSnapshots/{classroomId}/parentMessages/{messageId}`（§0-2。ルールの教室判定と
  保持期間の掃除をそのまま効かせるため、トップレベルには置かない）。

  | フィールド | 内容 |
  |---|---|
  | `classroomId` / `studentId` | **トークン doc の値**を使う（リクエスト body の値は信用しない） |
  | `studentName` | 保存時点の表示名（後で改名されても当時の宛名が分かる） |
  | `body` / `senderName` | 検証後の本文・送信者名（未入力なら空文字） |
  | `createdAt` | サーバー時刻 |
  | `notifiedAt` | null（室長が確認したら埋まる） |
  | `containsUrl` | 本文に URL らしき文字列を含むか（室長側の注意表示用） |

- 送信後は「受け付けました（返信はこのページには届きません。教室から電話・アプリでご連絡します）」を表示する。
  **返信は一方向**（オーナー確定）なので、保護者側に返信欄・受信履歴は作らない。

### E-2. 室長への通知（三点セット）

QR 提出通知と同じ構造を流用する（購読 → 選別 → モーダル → 既読のサーバー記録）。

1. **購読**: `parentMessages` を `classroomId == 現在の教室` で購読（教室分離。他教室の連絡は購読しない）。
2. **選別**: 起動時は `notifiedAt == null` の全件、実行中は新規到着分。選別は純関数に切り出してテストする。
3. **モーダル**: 「保護者からの連絡」（日時・生徒名・送信者名・本文）。`senderName` の横に
   **「送信者は本人確認をしていません」**の注記を必ず出す（なりすまし対策）。`containsUrl` が真なら
   「リンクが含まれています。開く前にご確認ください」を添える。
4. **既読**: モーダルの「確認」で callable `markParentMessagesNotified({ classroomId, messageIds })` が
   `notifiedAt` をサーバー時刻で埋める（localStorage に既読を持たない＝端末を替えても既読が保たれる）。

- Firestore ルール: `parentMessages` は **教室メンバーのみ read**、**write は不可**（Cloud Functions のみ）。
- 連絡履歴: **第1段は未実装**（通知モーダルのみ・§0 P-5）。Firestore には 365 日残るので、後から基本データ画面の
  生徒詳細に一覧を足せる。
- 保持期間: **365 日**。`retentionCleanup` の対象に `parentMessages` を追加する（`saveAttempts` / `operationEvents` /
  `lessonLedgerDays` と同じ個別 delete・予算制御の枠組み。バッチ削除に戻さない）。
- **本文の外部持ち出し禁止**: 保護者の文面は GitHub Issue・通知メール・AI へ渡す資料に**載せない**（個人情報）。

## F. 失効と在籍判定

- GET・POST とも、**当日（JST）の日付**で `isActiveOnDate(entryDate, withdrawDate, birthDate, today)` を評価し、
  偽なら拒否する（§G-2 の 4 段目）。
- したがって次が自動で成立する:
  - **入塾日前**: 閲覧不可（未来入塾の生徒に先にQRを渡しても入塾日まで開けない）。
  - **退塾日の前日**まで閲覧可。**退塾日当日から不可**（P-6・2026-09-15 改定＝生徒の退塾日は「その日から非在籍」。spec-basic-data §B）。
  - **高3卒業**: `hasGraduatedHighSchool` により卒業年度末（翌 3/31）の翌日（4/1）から不可
    （`resolveGraduationWithdrawDate` が返す補完日は 3/31 で、卒業生は 3/31 まで在籍＝自動補完日だけは「その日まで在籍」。spec-basic-data §B）。
- 管理データ画面用の「入塾日を在籍判定に使わない」規則（`resolveManagedRosterStatus`）は**使わない**。
  保護者ポータルは盤面・日程表と同じ `isActiveOnDate` に従う（判定の分散を作らない）。
- 失効・非在籍時の応答は **410 Gone** 相当で、画面は「このリンクは現在ご利用いただけません。教室へお問い合わせください」。
  **理由（退塾・卒業・失効）を出し分けない**（在籍状況が第三者に漏れないようにする）。

## G. セキュリティと教室分離

### G-1. 脅威モデル（ベアラートークンの限界）

- QR の写真が出回れば、第三者がその生徒の日程を見て連絡を送れる。**これは設計上の許容**であり、次で軽減する:
  - 表示情報の最小化（§C の非表示リスト。講師名・住所・料金・他生徒を出さない）。
  - 推測不能な 32 文字トークン＋Firestore に公開 read 文書を置かない（`boardShares` 型を採らない。§J-2）。
  - 室長がいつでも再発行（旧トークン失効）できる。
  - 退塾・卒業で自動失効。
  - 連絡の回数制限と本文長制限、「送信者の本人確認をしていない」旨の室長側表示。
- 関数のログに**本文・生徒名・トークン全文を残さない**（トークンは先頭 6 文字のみ記録）。

### G-2. 関数側の検証（INV-08・順序を変えない）

`parentPortalApi` は GET・POST とも次を**関数側で**検証する。1 つでも落ちたら以降を実行しない。

1. トークン文字列の形（`^[A-Za-z0-9_-]{16,64}$`。発行は 32 文字・§0-2）。
2. `studentPortalTokens/{token}` が存在し `revokedAt` が null。
3. **doc の `classroomId` を権威**として教室スナップショットを読む（リクエストのパラメータで教室を切り替えられない）。
4. **その教室のスナップショットに `studentId` の生徒が実在し、当日 `isActiveOnDate` が真**
   （＝「トークンの教室に生徒が実在し在籍」。他教室へコピーされたトークンはここで落ちる）。
5. 機能フラグ `parentPortalQr` がその教室で有効（§H）。

- 既存の `lectureSubmissionApi` は**トークン長しか見ておらず、教室所有権もレート制限も無い**。新 API では
  この穴を最初から塞ぐ（既存 API は無改変。§J-1）。
- 開発用教室（`v8OZ7zH8vONNHjjYVcR1`）対策: 写しの `parentPortalTokenClassroomId` によるクライアント側ガード
  （§B-3）と、上記 4 のサーバー側検証の**二層**で守る。クライアント側だけにしない（v1.5.415 の教訓）。
- CORS は必要最小限（GET/POST・`Content-Type` のみ）。`maxInstances` を設定して暴走コストを抑える。
- 実機検証は **staging** で行う。本番教室のトークンを開発端末で発行・解決しない（CLAUDE.md 本番データ保護ルール）。

## H. 機能フラグと段階公開

- フラグ名 **`parentPortalQr`**。O-1（`classrooms/{id}.featureOverrides`）は保留中のため、第1段は
  `featureRollout` の `development-only`（クライアント）＋サーバー側の同判定 `isParentPortalEnabledForClassroom`
  （開発用教室／テスト教室／staging プロジェクト）で制御する。**昇格は必ず両側同時**（§0-2）。
- OFF の教室では: 基本データ画面にQR表示・印刷・発行ボタンを出さない／`parentPortalApi` は GET・POST とも **403**
  （「現在ご利用いただけません」）。**トークン自体は失効させない**（ON に戻せば同じQRで復帰。P-11）。
- 公開順: 開発用教室 → staging 実機 → 本番 1 教室（オーナー指定）→ 全教室。
- フラグの評価は**サーバー側でも**行う（クライアントで隠すだけにしない）。

## I. 受け入れ条件（実装 Issue に載せるテスト可能な条件）

> 前提: §0 の値（P-1〜P-12）は 2026-09-13 に**推奨案のまま採用**して第1段を実装済み。オーナーが値を変えたら、
> §0 の表とこの節の数値を併せて書き換え、対応するテストも直す。

### K-2 トークン基盤

- 室長が「QR」ボタンを初めて押すと、その生徒に有効なトークンが 1 本だけ付く（2 回押しても増えない＝getOrIssue の冪等・§0-2）。
- 有効トークンがある生徒に再発行すると、旧トークンの `revokedAt` が埋まり、新トークンが 1 本だけ有効になる
  （有効トークンが 2 本同時に存在しない）。
- 失効済みトークンで GET すると 410 になり、再発行しても**古いトークンは復活しない**。
- 生徒を名簿削除すると、その生徒のトークンが `revokedReason='studentDeleted'` で失効する。
- `stripParentPortalToken` は `parentPortalToken` と `parentPortalTokenClassroomId` の**両方**を落とす
  （片方だけ残さない）。教室コピー後の `StudentRow[]` にトークン系フィールドが 1 つも残らない。
- `stripForeignParentPortalToken` は発行元教室が一致する行を**変更しない**（自教室のQRが消える回帰を作らない）。
- `npm run test:rules`: 認証済みの室長でも `studentPortalTokens` を read/write できない。`parentMessages` は
  自教室のみ read でき、write は全員不可。

### K-3 日程計算 `buildParentScheduleView`

- 盤面 `weeks` にある日はテンプレ展開で行が増えない（盤面優先。盤面に配置が無い日は「予定なし」）。
- 盤面に無い未来日はテンプレ展開され、全行に「予定（変更の可能性あり）」が付く。
- `templateFreezeBeforeDate` より前の日付はテンプレ展開しない。
- 休講日（`holidayDates` / `closedWeekdays`）は授業行が 0 件。`forceOpenDates` の日は通常どおり出る。
- 講習期間（`startDate ≤ 日 ≤ endDate`）の日は、通常授業の配置があっても行が出ず「講習期間」1 行になる。
  期間の前日・翌日は通常どおり出る（境界の両端を含むことを固定）。
- 欠席（`absent`）の日は「お休み」＋振替先の日付・限が出る。**振替先が `attended` でも振替先が出る**（P-10 回帰テスト）。
- `moved` の行は出ない（移動先だけが 1 回出る＝同じ授業が 2 回出ない）。
- `special`（講習コマ）は講習期間外に置かれていても出ない。
- 同名の別生徒がいても、`managedStudentId` が一致する生徒の予定だけが出る。
- 応答に講師名・机番号・他生徒名・在庫数が**1 つも含まれない**（JSON を文字列化して検査）。
- クライアントと functions 同梱版が**同じ fixture で同じ結果**を返す（二重実装のドリフト検出）。

### K-4 API とページ

- 32 文字でないトークン、存在しないトークン、`revokedAt` 済みトークンはいずれも 400 / 410 で、
  **教室スナップショットを読みに行かない**（読んでから弾く実装にしない）。
- トークンの教室に `studentId` の生徒が存在しない場合は 410（他教室へコピーされたトークンの遮断）。
- リクエストに `classroomId` を付けても、応答はトークン doc の教室の内容になる（パラメータで教室を切り替えられない）。
- POST: 本文 0 字・501 字・制御文字のみは 400。500 字ちょうどは成功。
- POST: 同一トークンで 1 日 6 件目は 429（5 件目までは成功）。JST 0:00 を跨ぐとカウントが戻る。
- `parentMessages` の `classroomId` / `studentId` はリクエスト body ではなくトークン doc 由来の値になる。
- 応答ヘッダに `Cache-Control: no-store` が付く。
- `/p/{token}` は App 本体（認証・Firestore 購読）を読み込まない。

### K-5 通知・履歴・保持

- 室長が教室を開くと、`notifiedAt == null` の自教室の連絡がモーダルに出る。**他教室の連絡は出ない**。
- 「確認」で `notifiedAt` がサーバー時刻で埋まり、別端末で開いても再通知されない。
- モーダルに「送信者は本人確認をしていません」が常に表示される。
- 365 日より古い `parentMessages` が retention 掃除で削除され、それ以内は残る。
- フラグ `parentPortalQr` が OFF の教室では GET・POST とも 403 になり、ON に戻すと**同じトークンで**復帰する。

### K-6 基本データ画面

- 在籍中の生徒にだけQR表示・印刷・再発行のボタンが出る（退塾・卒業済みには出ない）。
- QR の URL は `/p/{token}` 形式で、講習提出の `/s/{token}` と取り違えない。
- 再発行ボタンは確認ダイアログを挟み、実行後に画面のQRが新トークンへ切り替わる。
- 印刷は 1 生徒 1 枚（生徒名・教室名・QR・短い案内文）。盤面・日程表の印刷レイアウトに影響しない。

## J. 既存仕様との関係

### J-1. 講習提出（`spec-special-session-submission.md`）とは別物

- 提出トークン（`submissionToken`・**講習セッションごと**）と保護者ポータルトークン（**生徒ごと・恒久**）は
  別のコレクション・別の URL・別の関数。`lectureSubmissionApi` は**無改変**とし、保護者ポータルの都合で
  提出 API を触らない（INV-07「提出データの確定不変」に触れないため）。
- 保護者ポータルは **読み取りのみ**（`parentMessages` の追加を除く）。盤面・在庫・提出・出欠へ一切書き込まない。

### J-2. 配布用盤面（`boardShares`）の型を採らない理由

- `boardShares/{token}` は**公開 read の Firestore 文書**で、盤面 state が変わるたび `setDoc` する（デバウンスなし）。
  生徒ごとに同じ方式を採ると、(a) 生徒数 × 編集回数の書込コスト、(b) 個人情報を含む公開文書の常駐、
  (c) 失効・再発行の手段が無い、の 3 点で不適。
- よって保護者ポータルは**オンデマンド関数型**（公開文書を置かず、アクセス時に関数がスナップショットから組み立てる）。
  これは `/s/{token}` の提出ページと同じ構造。

### J-3. 基本データ（`spec-basic-data.md`）

- `StudentRow` に `parentPortalToken` / `parentPortalTokenClassroomId` を**任意フィールド**として追加する
  （未設定＝未発行。後方互換）。在籍判定・盤面・請求・集計の計算には一切影響させない
  （`isExternal` と同じく「実データの意味を変えない追加」にとどめる）。
- 既存データの移行は不要（発行するまでフィールドが無い状態が正）。

### J-4. 日程表・PDF（`spec-schedule-pdf.md`）

- 保護者ポータルの表示は生徒日程表とは**別経路**。日程表 HTML・印刷レイアウトは変更しない。
- 「休み → 振替先」の意味だけは生徒日程表と一致している必要がある（§D-5）。食い違いが見つかったら
  日程表側を触る前に、本仕様と `buildLinkedLessonDestinationMap` の対応を確認する。
