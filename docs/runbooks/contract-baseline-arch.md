# Runbook: 契約時環境（株式会社アーチ）の固定と復旧計画

> **作成**: 2026-09-19。**対象**: 株式会社アーチ（`workspaces/main`・緑が丘校／日大前校）との契約時点のアプリ環境。
> **目的**: 「契約した時点のアプリ」を**いつでも同じものとして出し直せる**状態を保ち、万一の障害・誤デプロイ・
> データ破損のときに**数分〜数十分で復旧**できるようにする。判断フローの正本は
> [safe-release スキル](../../.claude/skills/safe-release/SKILL.md)、症状別の戻し方は [rollback.md](./rollback.md)。
> 本書は「基準点の定義（§1）」「復旧計画（§3）」「オーナー作業（§4）」「訓練と更新（§5〜6）」を定める。

---

## 0. 結論（先に要点）

- **契約時環境 ＝ Git タグ `contract/arch-2026-09-19`**（commit `48e9e19`・アプリ版 **v1.5.552**）。ライブ本番と同一。
- 戻し方は **Actions →「Restore contract baseline」**（`.github/workflows/restore-baseline.yml`）。
  指定した ref を checkout して Hosting／Functions／ルールをそのまま出し直す。**main には触れない**ので main が壊れていても戻せる。
- **復旧は二段構え（§3-0）**。第一手は **`stable`（＝オーナーが「問題なし」と確認した直近の版）**、
  それでも駄目なら**契約時タグ（必ず動く床）**。契約時環境へ戻すと契約以降の改良が全部消えるので、常用の戻し先にはしない。
- コードは Git（タグ）で守られる。**守られていないのは次の 3 つ**で、§4 のオーナー作業で埋める:
  1. **データ**（Firestore／Storage）… 自動バックアップはあるが「契約時点」という名前の固定スナップショットは無い。
  2. **秘密情報**（GitHub Secrets・サービスアカウント JSON・Drive の OAuth）… Git に無く、GitHub からは読み返せない。
  3. **Hosting のリリース履歴**… Firebase コンソールのロールバックは保持世代（既定 5）を超えると消える。

## 2. 何がどこで守られているか（現状の防御と穴）

| 守る対象 | 今の守り | 穴 | 埋め方 |
|---|---|---|---|
| フロントのコード | Git（タグ）＋ Hosting リリース履歴 | Hosting 履歴は保持世代（既定 5）を超えると消える → コンソールでのロールバック先が無くなる | **Restore ワークフロー**（Git から再ビルド）。加えて §4-3 で保持世代を増やす |

## 3. 復旧計画（症状 → 手順 → 目安時間）

> 大原則: **まず止血（戻す）→ 次に原因調査**。データ復元だけは教室を取り違えると他教室を壊すので、慌てず対象教室を確認する。

### 3-0. どこへ戻すか（戻し先の選び方・全症状に共通）

障害の原因はほとんど直近の変更なので、**第一手は「直近の正常版」**。契約時環境は最後の砦として温存する。

| 順 | 戻し先 | 指定する ref | 何が戻るか |
|---|---|---|---|
| ① | **直近の正常版**（第一候補） | `stable` | オーナーが「問題なし」と確認した最後の版。契約以降の改良は保たれる |
| ② | 特定の版 | `release/vX.Y.Z` | その版ちょうど（`stable` より前に戻したい・原因の版が分かっているとき） |
| ③ | **契約時環境**（床） | `contract/arch-2026-09-19` | 契約時点。**契約以降の改良は全部消える**ので最後の手段 |

- `release/*` は本番デプロイのたびに CI が自動で打つ（`deploy-firebase-hosting.yml`）。**版とコミットが 1 対 1 で引ける**ので、
  「コンソールの時刻を見て人が思い出す」必要がない。
- `stable` は**オーナーが進める印**。Actions →「**Mark live as known-good (stable)**」を入力なしで実行すると、
  いまライブに出ている版へ印が進む。**確認リストを一通り確認して問題なかったリリースの直後に押す**のが運用。
  押し忘れても困らない（`stable` は最後に押した版を指したままで、それは「動くと分かっている版」なので安全側）。
- 印を進められるのは main の履歴にある版だけ（未マージのブランチは記録できない）。契約時タグへ `stable` を進めることはできない（床は動かさない）。
- 復旧が済んだら、**回復した版を改めて known-good に記録**する（次の障害の戻し先になる）。

### 3-A. 画面が壊れた（真っ白・JS エラー・操作不能）— フロントを契約時に戻す

| 手順 | 所要 |
|---|---|
| A-1 直近のデプロイが原因なら [rollback.md A-1](./rollback.md)（Firebase コンソール → Hosting → 前リリースへロールバック） | 1 分 |
| A-2 それで戻せない（履歴が消えた・複数版前・main が壊れている）なら **Actions →「Restore contract baseline」** を `project=komahyouapp-prod` / `target=hosting` / `confirm=RESTORE komahyouapp-prod` で実行 | 約 3 分 |
| A-3 各端末でハードリロード（Ctrl+Shift+R）。`version.json` が **1.5.552** を示せば基準点が出ている | 1 分 |
| A-4 恒久対応: 原因コミットを `git revert` して main へ（通常 CI）。**それまで main に push しない**（push すると最新 main が再デプロイされて基準点を上書きする） | — |

### 3-B. サーバー処理が壊れた（保存・QR 提出・保護者ページ・バックアップが失敗）— Functions を契約時に戻す

| 手順 | 所要 |
|---|---|
| B-1 「Restore contract baseline」を `target=functions`（本番なら confirm 必須）で実行 | 約 3〜5 分 |
| B-2 実反映の確認: 保存 1 回（**開発用教室 `v8OZ7zH8vONNHjjYVcR1` で**）・QR 提出 1 件・`version.json` は無関係なので `gcloud functions describe` の updateTime か実動作で見る | 5 分 |
| 注意 | `--force` のため、基準点より後に追加された関数は消え、削除された関数は復活する（＝基準点の一式に揃う）。後から追加した機能の画面はエラーになるので、フロントも同時に戻す（`target=hosting+functions`）のが安全 | — |

### 3-C. 権限エラー（保存が permission-denied・他教室が見える）— ルールを契約時に戻す

| 手順 | 所要 |
|---|---|
| C-1 「Restore contract baseline」を `target=rules` で実行（SA に権限が無く赤なら Firebase コンソール → Firestore → ルール にタグ時点の `firebase/firestore.rules` を貼って公開） | 3 分 |
| C-2 `npm run test:rules` が通る内容であることを手元で確認してから出す（ルールは fail-open にすると全教室に波及） | — |

### 3-D. データが壊れた・消えた（教室のデータ／他教室のデータが出る）— 最重要・慎重に

| 手順 | 所要 |
|---|---|
| D-1 [rollback.md C](./rollback.md) に従い、**対象教室を開いてから**自動バックアップ（15 分刻み 24h／毎時 72h／日次 400 日）から復元。復元前に incident backup が自動で取られる（90 日） | 10〜30 分 |
| D-2 契約時点に丸ごと戻したいときだけ **§4-1 の契約時スナップショット**（JSON）を開発者画面「バックアップを読み込む」で取り込む。**契約以降の入力は全部消える**のでオーナー判断で | 10 分 |
| D-3 Firebase 側が全滅（プロジェクト消失・Storage 消失）なら Drive ミラー／ローカル控え → 新プロジェクトへ（3-E） | — |
| Claude の制約 | 本番への書き込み復元は行わない。手順提示と**読み取り照合**まで。実行はオーナー | — |

### 3-E. 環境そのものを失った（Firebase プロジェクト・GitHub が使えない）— 再構築

1. **GitHub が使えない**: ローカル clone（§4-5）から `git push` で新リポジトリへ。タグも `git push --tags`。Secrets は §4-2 の控えから再登録。ワークフローはそのまま動く。
2. **Firebase プロジェクトを失った**: `docs/runbooks/staging-setup.md` の手順（staging を作った手順と同じ）で新プロジェクトを作る → Secrets を新プロジェクトのものに差し替え → 「Restore contract baseline」で `hosting+functions` と `rules` を出す → §4-1 のスナップショットを開発者画面から読み込む → QR・共有リンクは URL が変わるので再配布。所要は半日〜1 日（クラウド側の作成と権限付与が大半）。
3. **Google アカウント（オーナー）を失った**: 上の両方に波及する。§4-2 の控えを別の管理者にも渡しておく。

## 4. オーナー作業（今回やること・チェックリスト）

Claude の実行環境からはできない（本番書き込み・秘密情報・クラウド権限）ため、オーナーに実施してもらう。
**上から順に、0〜2 は契約直後に必ず**。

### 4-0. 基準タグを GitHub に push する（必須・2 分）
Claude の実行環境からはタグを push できない（セッションの権限がブランチ限定で 403）。ローカルにはタグを作ってあるが
GitHub には未登録なので、認証済み PC で次を実行する（タグは bump コミット `48e9e19` に打つ）:
```bash
git fetch origin main
git tag -a contract/arch-2026-09-19 48e9e19 -m "契約時環境(株式会社アーチ) v1.5.552"
git push origin contract/arch-2026-09-19
```
- [ ] GitHub → Tags に `contract/arch-2026-09-19` が見える。
- タグを push するまでの間に復旧が必要になったら、Restore ワークフローの `ref` に**コミット SHA `48e9e19`** を入力すれば同じものが出る。

### 4-1. 契約時データスナップショットを別置きする（必須）
- [ ] 本番アプリを**管理者**で開き、開発者画面の「ワークスペース全体 JSON 書き出し」（`docs/spec-save-restore.md` §5-2）で 1 ファイル保存。
  ファイル名例: `komahyou_契約時環境_arch_2026-09-19.json`。
- [ ] 保存先を **2 か所**に: ①ローカル PC ②Google Drive の**バックアップ用フォルダの外**に作った `契約時環境/` フォルダ
  （バックアップ用フォルダ内は自動間引きされる。外に置いたものは間引かれない＝ §8-2 の逃げ道）。
- [ ] 併せて Drive ミラーの **2026-09-19 JST 3:00 の日次 `.json.gz`** も同じ `契約時環境/` へコピー（サーバー側と同一のバイト列・可逆）。
- [ ] 本書 §1 の「契約時データスナップショット」行に、ファイル名と保管場所を追記する。

### 4-1b. オフライン（手元 PC）への定期控え（必須・2026-09-19 オーナー方針）

**現状の穴**: 15 分ごとの自動バックアップは**本番と同じ Firebase プロジェクトの中**にある。プロジェクトを失う・
課金停止・アカウント停止のときはデータ本体と一緒に消える。実質的な避難先は Google Drive ミラーだけで、
それも 400 日で**ゴミ箱を経由せず完全削除**される。**PC へ自動で降りてくる経路は今のところ無い**
（保存失敗時の JSON 自動退避は障害時だけで、定期ではない）。

方針は次の 2 本立て（オーナー選択）。

- [ ] **① Google Drive for desktop で PC に同期する（設定のみ・5 分・容量 約 3GB）**
  - Drive for desktop を入れ、バックアップ用フォルダを**「オフラインで使用可能」**（ミラーリング）に設定する。
    これで 15 分ごとのミラーが PC のディスクにも自動で降り、Firebase を失っても手元に JSON が残る。
  - **注意**: ミラーなので**削除も同期される**。400 日の間引きで Drive から消えたものは PC からも消える。
    「この時点を必ず残す」ものは、§4-1 と同じく**間引き対象外のフォルダ（`契約時環境/` など）へコピー**して置く
    （間引き対象は設定フォルダ内のファイルだけなので、外へ出せば残る）。
- [ ] **② 月次の手動 JSON 書き出し（5 分・毎月 1 回）**
  - 開発者画面の「ワークスペース全体 JSON 書き出し」で 1 ファイル保存し、`月次バックアップ/YYYY-MM.json` として
    ①のフォルダ外へ置く。**自動の間引き・同期の影響を受けない独立した控え**になり、
    「半年前の状態を見たい」に応えられる（自動バックアップの日次 400 日とは別系統の保険）。
  - 実施記録は §5 の表に 1 行追記する（やったかどうかが後から分かるように）。

> 完全自動で PC へ落とすには PC 側の定期実行（Windows タスクスケジューラ＋`gcloud storage cp`）が要る。
> GitHub Actions は PC にファイルを置けないので、自動化の置き場所はクラウドではなく PC 側になる。
> 今回は①②で運用し、必要になったらスクリプトを用意する。

### 4-2. 秘密情報の控え（必須）
- [ ] 次を**パスワードマネージャ等の安全な場所**に控える（GitHub Secrets は登録後に読み返せない）:
  `FIREBASE_WEB_ENV`（＝ `.env.local` の内容）、`RE_FIREBASE_SERVICE_ACCOUNT`（SA の JSON・失くしたら GCP で再発行）、
  `PROD_FUNCTIONS_ENV`（＝ `functions/.env`・Drive の OAuth 一式）、staging の 3 つ。
- [ ] 契約書・請求担当の連絡先と併せて、**Claude 以外の第三者（自分の予備アカウント等）でも再構築できる**状態にする。

### 4-3. Hosting の保持世代を増やす（推奨・5 分）
- [ ] 認証済み PC で `node tools/firebase-hosting-retention.mjs --site komahyouapp-prod --count 30`（既定 5 → 30）。
  これで Firebase コンソールのロールバック先が 30 デプロイ分残る（1 日に数回デプロイしても 1 週間以上）。
  ※ 既定は `docs/spec-save-restore.md` §8-1 補足の「5 世代・手動運用」。変えたら同節も 30 に直す。

**料金への影響（2026-09-19 実測・v1.5.552 のビルドで計算）**

| 項目 | 値 |
|---|---|
| 1 デプロイ分の配信物（`dist`） | **4.72MB**（24 ファイル・gzip 2.49MB）。最大は `App-*.js` 1.70MB |
| 5 世代（現状） | 最大 約 24MB |
| 30 世代 | 最大 約 **142MB**。実際はファイル単位でハッシュ名＝**変わっていないチャンクは共有**されるので、1 回のデプロイで増えるのは実質 `App-*.js`＋CSS＋`index.html`＋`version.json` の約 1.8MB。30 世代でも **約 70MB** に収まる見込み |
| Firebase Hosting の料金（公開価格・変動あり） | ストレージは **10GB まで無料**、超過分 約 $0.026/GB/月。転送は 360MB/日まで無料、超過 約 $0.15/GB |
| 結論 | 142MB は無料枠 10GB の **約 1.4%**。**追加費用は実質ゼロ**（仮に課金対象でも 0.14GB × $0.026 ≒ **月 $0.004**）。**転送量は増えない**（配信されるのは常に現行版 1 つだけで、保持分は保管のみ） |

- 混同しない: 過去に問題になった「46GB の請求」は **Cloud Storage のバックアップ残置**（§8-1a・別サービス）で、Hosting の保持世代とは無関係。
- 世代を増やすデメリットは事実上ない（Firebase コンソールのリリース一覧が長くなるだけ）。100 世代にしても無料枠内だが、
  ロールバック先を人が選び間違えるリスクが上がるので **30 前後が妥当**。

### 4-4. 復旧訓練を 1 回やる（推奨・15 分）
- [ ] Actions →「Restore contract baseline」を **`project=komahyouapp-staging` / `target=hosting+functions`**（confirm 不要）で実行 → 緑。

## 6. 基準点の更新ルール

- 契約更新・大きな仕様変更（会社レイヤの本格運用、Hosting multi-site 化など）を本番に出して**安定を確認した後**に、
  新しいタグ `contract/arch-<YYYY-MM-DD>` を打ち、本書 §1 を差し替える。
- **旧タグは消さない**（当時の環境に戻る手段として残す）。
- タグは main のリリース版（CI の bump コミット）に打つ。ライブ `version.json` と `package.json` が一致していることを確認してから。
  ```bash
  git fetch origin main
  git tag -a contract/arch-<日付> <bumpコミット> -m "契約時環境(株式会社アーチ) v<版>"
  git push origin contract/arch-<日付>
  ```
- Restore ワークフローの `ref` 既定値も新タグへ更新する（旧タグは `ref` に手入力すれば使える）。

## 7. Claude が守ること（自動セッションの制約）

- 本番 Firestore／Storage への**書き込み・復元は行わない**（CLAUDE.md 本番データ保護ルール）。データ復旧はオーナーが実行し、Claude は手順提示と読み取り照合まで。
- 「Restore contract baseline」の**本番実行**（`confirm=RESTORE komahyouapp-prod`）は本番の配信物を差し替える操作なので、オーナーの明示指示があるときだけ行う。staging への訓練実行は指示なしで行ってよい。
- タグ `contract/*` の**削除・付け替えはしない**。

## 8. 今後の改造との関係（復旧計画を腐らせないための約束）

この復旧計画は**通常の開発フローに一切割り込まない**。追加したのは「手動ワークフロー 1 本・ドキュメント・テスト 1 本」だけで、
`main` への push で動く CI（lint / unit / build → 本番デプロイ）の挙動は変えていない。Restore ワークフローは
`workflow_dispatch` のみ（push・schedule では絶対に発火しない。`tools/restore-baseline-workflow.test.mjs` で固定）。

一方、**放っておくとズレて「いざ戻したい瞬間に動かない」**箇所が 5 つある。改造のたびに次を守る。

| # | 干渉しうる改造 | 何が起きるか | 守り方 |
|---|---|---|---|
| 1 | 通常デプロイに**新しい secret・必須 VITE 変数・ビルド手順**を足す | Restore 側は古い手順のままなので、復旧実行時に初めて失敗する（普段実行しないので気付けない） | **`tools/restore-baseline-workflow.test.mjs` が CI を赤にする**（secret の欠落・必須 VITE キーの不一致を検知）。赤になったら `restore-baseline.yml` にも同じ変更を入れる |
| 2 | **データ構造の移行**（フィールドの改名・意味の変更・別コレクションへの移動） | 基準点のコードは移行後のデータを知らない。**古いコード × 新しいデータ**で誤読・表示欠落が起きうる（追加だけのフィールドは無視されるので無害） | 移行は「旧形式も読める」形（追加のみ・旧フィールドを消さない）で入れる。消す移行をしたら**その時点で新しい基準点タグを打ち直す**（§6）。Runbook §1 の台帳も更新する |
| 3 | **Cloud Functions の追加・削除** | Restore の functions は `--force`＝基準点の一式に完全に揃える。後から足した関数は**消える**、消した関数は**復活する** | 復旧は原則 `hosting+functions` を**セットで**戻す（フロントと関数の版を合わせる）。`functions` 単独で戻すのは「サーバー処理だけが壊れた」ときに限る |
| 4 | **新しい Firestore コレクション・ルール変更** | 基準点のルールは新コレクションを許可しない（例: `parentMessages`）。ルールだけ戻すと新機能が権限エラーになる | ルール単独の復旧は「権限事故の止血」専用。機能を戻すなら hosting/functions と揃える。ルールは CI 対象外なので、変更したら本番反映を忘れない |
| 5 | **複数会社展開（Hosting multi-site・会社ごとの env）**<br>`docs/plan-2026-09-18-second-company-onboarding.md` | サイトが増えると「どのサイトを戻すか」の指定が必要になる。今の Restore は 1 サイト前提 | multi-site を入れる**同じ変更のなかで** `restore-baseline.yml` に `site` 入力を足す（テストは secret とキーのズレしか見ないので、ここは人が見る）。会社ごとに基準点タグを分けるかは §6 で判断 |

| 6 | **リリース運用の変更**（版の付け方・デプロイ経路の変更） | `release/*` タグが打たれなくなると「直近の正常版」を機械的に指せなくなり、戻し先が人の記憶に戻る | `tools/restore-baseline-workflow.test.mjs` が release タグ付与と `stable` の手動更新を固定している。デプロイ経路を変えるときはこのテストも一緒に見直す |

**そして最も大事な運用上の約束**: 復旧の第一手は常に「**直近の正常版へ戻す**」（`stable` / Hosting ロールバック / `git revert`）。
契約時環境へ戻すのは**最後の手段**で、契約以降の改良が全部消える。改造を積み上げるほどこの差は大きくなるので、
**四半期ごと、または大きな改造が本番で安定したタイミングで新しいタグを足す**（§6・旧タグは残す）。こうすると
「契約時に戻す」と「直近の安定版に戻す」を別々に持てて、改造が進んでも復旧の選択肢が劣化しない。
