# 質問・要望 → フィードバック → QA の充実（運用の輪）

> オーナー指示（2026-10-16 夜）「質問や要望が蓄積されて、フィードバックや QA の充実に繋げられるような仕組みにして」。
> 仕様の位置づけは `docs/spec-developer-report.md` §G-6（QA 公開）。公開の場は `qaEntries` の画面ではなく、**説明書 `docs/user-manual.md` の
> 「11. よくある質問」**とする（全教室共有・開発者が 1 件ずつ明示的に足す・足す前に本文を編集できる、という §G-6 の既定どおり。
> 説明書は AI 即時回答の根拠でもあるので、QA を足すほど AI の回答も良くなる）。

## 1. 輪の全体

| 段 | 何が起きるか | どこに残るか | だれが |
|---|---|---|---|
| ① 蓄積 | 室長が「質問・要望」を送る。AI 即時回答（主 Sonnet・影 Haiku）・開発者の回答・解決済み・Issue 番号がそろう | `developerReports/{id}`（自動） | 自動 |
| ② 集める | 整理していない質問・要望を 1 本の **QA 候補パック** にする。先頭に整理の指示文。AI が答えられなかった質問を最優先に並べる | `local/qa-digests/`（Git 管理外） | Claude（`tools/question-qa-digest.mjs`・読み取りだけ） |
| ③ 整理 | パックを読んで、似た質問を束ね、QA 案・説明書の修正案・要望の一覧・対象外に分ける | 返答（チャット） | Claude（spec-curator の領分） |
| ④ 承認 | QA 案と修正案を見て、載せるものを決める | — | **オーナー** |
| ⑤ 直す | 説明書 11 章に QA を足す／章を直す → `sync-shared` → main へマージ（＝デプロイ） | `docs/user-manual.md`・`functions/src/generated/userManual.ts` | Claude |
| ⑥ 記録 | 整理した受付番号を記録に書く。次回のパックから外れる | `docs/qa-curation-log.md` | Claude |
| ⑦ 確かめる | 評価ワークフローを流し、足した QA で AI が答えられるようになったかを見る（必要なら評価の質問も足す） | Actions「Question AI eval」 | Claude |

要望（category=request）は QA にはならないので、③で一覧にして **bug-triage スキルで Issue に起票**し、記録には `要望 Issue #n` と書く。

## 2. いつ回すか

- **月に 1 回**（月初）か、**開発用教室で AI の回答が「自動回答を作れませんでした」になった報告が溜まったとき**。
- 全教室へ AI 即時回答を広げたあとは、**2 週間に 1 回**を目安にする（質問の量を見て調整）。
- 1 回の所要は ②③ で 15 分程度（件数による）。費用は ⑦ の評価 1 回約 115 円だけ（②③は API を呼ばない）。

## 3. 手順（Claude が行う）

```bash
export FIRESTORE_ACCESS_TOKEN=$(node tools/prod-readonly-token.mjs)
node tools/question-qa-digest.mjs --workspace main              # 既定: 直近 90 日・整理済みを除く
node tools/question-qa-digest.mjs --workspace main --since 2026-09-01
node tools/question-qa-digest.mjs --workspace main --all        # 整理済みも含めて見直すとき
```

1. 出力された `local/qa-digests/qa-digest-<時刻>.md` を読む（**生徒名を含むので、リポジトリ・Issue・公開ログへ貼らない**）。
2. パック先頭の指示文どおりに整理し、オーナーへ「QA 案」「説明書の修正案」「要望の一覧」「対象外」を提示する。
   - QA は利用者の言葉で、画面の言葉だけで、個別の中身は一般化する（説明書の書き方に合わせる。生徒名・教室名・日付を残さない）。
   - 開発者の回答（answerFinal）があるものはそれを正とする。AI の回答と食い違っていれば、説明書のどの章が足りないかも書く。
   - 説明書に根拠が無い QA は「要確認」とし、必要なら `docs/spec-*.md` を読んで確かめる。仕様が無い・曖昧なら spec-curator へ。
3. オーナーの承認を得たものだけを `docs/user-manual.md`「11. よくある質問」へ足す（章の参照番号を添える）。本文の修正も同じコミットで。
4. `npm --prefix functions run sync-shared` を回し、テスト（`questionAiAnswer.test.ts` が説明書の複製のズレを検出）→ `CHANGELOG.md` → main へマージ。
5. `docs/qa-curation-log.md` に受付番号・処理日・結果・反映先を書く（同じコミットでよい）。
6. 評価ワークフローを流して、足した QA に関する質問が答えられるかを見る。足りなければ評価の質問（`questionAiEvalCases.ts`・確認リスト qa-q*）も足す。

## 4. やってはいけないこと

- Firestore へ書かない（整理の状態は `docs/qa-curation-log.md` にだけ持つ。`developerReports` に印を付けるために書き込まない＝本番データ保護ルール）。
- オーナーの承認なしに説明書へ QA を足さない（§G-4 の基準は QA 公開の前提条件。公開はさらに「特定の教室でしか成り立たない前提を含まない」）。
- パック（生徒名を含む）をコミット・Issue・チャット以外へ出さない。`local/` は Git 管理外。

## 5. 室長側のフィードバック（未実装・オーナー判断待ち）

いまの輪は「AI の回答 → 開発者の回答 → 説明書」で閉じている。室長が **AI の回答に「役に立った／立たなかった」を返す**仕組みを足すと、
整理の優先順位がより正確になるが、室長の画面（送信後の結果画面・履歴タブ）が変わる＝ユーザビリティ影響なので、
CLAUDE.md の方針どおり懸案と妥協案を先に出す。

- 懸案: ボタンが増える（学習コスト）／押されない可能性が高い／否定的な評価を開発者がどう扱うかの決めが要る。
- 妥協案 A（軽い）: 結果画面に「この回答で解決しましたか？ はい／いいえ」の 2 択だけ。押さなくてもよい。`developerReports/{id}.aiAnswerFeedback` に記録し、パックで「いいえ」を最優先にする。
- 妥協案 B: 「いいえ」のときだけ一言入力欄を出す（何が違ったか）。
- 妥協案 C: 作らない。開発者の回答と AI の回答の食い違いだけを見る（現状）。

採用するなら、仕様（§G-7）・ルール（`reportAnswers` への書き込みは CF のみ）・確認リスト・評価の順で足す。
