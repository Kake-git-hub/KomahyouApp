### 補足
- 自動保存の「重さ」は既に対策済み（盤面グリッド memo 化／週数の上限トリム／clone・stringify をデバウンス後へ移動）。
  自動保存自体は現状のパフォーマンス主因ではないため残す。

### 多端末競合の防止（楽観ロック）— 2026-07-04 確定・オーナー確認済み（監査 B1）

想定運用は「1端末でオンライン作業」だが、万一2端末目が同じ教室を編集した場合の**唯一の防波堤**として
楽観ロック（版数照合）を実装している。**過去のクロス汚染事故（他教室データでの上書き）への意図的な
破壊防止ガードであり、消してはならない。**

- クラウド保存は教室スナップショットの `version`（保存ごとに +1）で楽観ロックする。クライアントは
  「読み込んだ時点の版数（baseVersion）」を送り、サーバー版数と不一致なら**上書きせず拒否**する
  （`failed-precondition`。`functions/src/index.ts` `resolveOptimisticVersionDecision`）。
- 衝突時、このタブは (1) 内容を**JSON バックアップへ自動退避**、(2) 以後の**クラウド同期を停止**
  （古いベースでの再送ループを断つ）、(3) 「別の端末でこの教室のデータが更新されました。画面を再読み込みして
  ください」と**再読み込みを促す**。ローカル保存（IndexedDB）は継続するため編集内容はブラウザ内に残る。
- 版数は時刻比較では代替できない（多端末の時計ズレで誤判定するため必ず版数で照合する）。

### 1教室1タブ制約の範囲 — 2026-08-29 明文化・オーナー確定

「同じ教室を2つ開かせない」ロック（`useClassroomTabLock`）は **BroadcastChannel ＝ 同一ブラウザ（同一プロファイル）内の
タブ間でのみ**成立する。**別端末・別ブラウザ・シークレットウィンドウからの同時オープンは検知できない**。

- 検知できたときは後から開いたタブを**ブロック**する（開発者ロールは対象外。BroadcastChannel が無い環境では機能無効＝ブロックしない）。
- したがって**多端末の同時編集を防ぐ唯一の実効ガードは楽観ロック（版数照合・上記）**であり、タブロックは同一ブラウザでの
  うっかり二重オープンを減らす補助にすぎない。**タブロックがあるから多端末は安全、と読み替えてはいけない。**
- **UI で追加の警告は出さない**（2026-08-29 オーナー確定＝仕様として明文化するのみ）。運用は「1教室1端末」を前提とし、
  多端末衝突は楽観ロックの再読み込み案内で吸収する。

## 2. 保存失敗時

- **原則、自動リトライしない。**
  - **【2026-07-04 確定・オーナー確認済み／C2：例外を明文化】** ただし**一時的（transient）な同期エラーに限り、
    最大3回まで自動再試行**する（`manualFirebaseSaveStability`。ネットワーク瞬断・409 等の一過性失敗を吸収するため）。
    **恒久失敗（非 transient）および版数衝突（多端末上書き）は再試行せず**、下記の JSON 退避＋作業指示へ進む
    （版数衝突は同じ古いベースで再送しても必ず失敗するため、クラウド同期を停止して再読み込みを促す。§1「多端末競合の防止」参照）。
- JSON バックアップを**自動でダウンロードフォルダへ書き出す**。
- ダイアログで「再ログインして、ダウンロードフォルダのバックアップを読み込んでください」と作業指示を出す。

### 保存時の3層防御（破壊防止ガード）— 2026-07-04 確定・オーナー確認済み（監査 B2）

Cloud Function `saveClassroomSnapshot` は保存時に次の3層で本番データを守る。**いずれも過去のクロス汚染・
偽 dirty 上書き事故（他教室データや空データでの上書き）への意図的な破壊防止ガードであり、消してはならない。**

1. **空データ上書き拒否**（`assertNoSnapshotDataLoss`）：既存に教室管理データがあるのに、空（管理データ0件）の
   ペイロードで上書きしようとした保存は `failed-precondition` で拒否する（前回件数を添えて中止）。
2. **保存後の読み戻し検証**：保存直後に Firestore から読み戻し、`payloadHash` が一致しなければ `internal` で失敗させる
   （サイレント破損＝壊れたまま「保存済み」表示になる事故を防ぐ）。
3. **saveId による冪等リプレイ**：同一 `saveId`・同一内容の再送は再保存せず検証済み結果を返す。同一 `saveId` で
   内容が異なる再送は `already-exists` で拒否する（ネットワーク再試行の二重書き込み・取り違えを防ぐ）。

- **週単位の分割保存（§9・2026-10-27 方式採用・段階 0〜A 実装済み・保存側の B は未実装）での実装は §9-4-6**。3 層とも残し、版数照合はトランザクション内へ、
  読み戻し失敗時は目次を直前の内容へ戻す形に強化する。

## 4. 復元（4種類 → 1種類へ統合）

| 機能 | 扱い |
|------|------|
| 直前の Firebase 保存前へ戻す | **削除**（Undo で代替） |
| サーバーバックアップから復元 | 各教室画面から**削除**、**開発者画面のみ**へ移動。**【2026-09-18 改定】室長が自教室だけを復元する入口を §4-1 の条件で教室画面へ戻す** |
| ローカル自動バックアップから復元 | **削除** |
| JSON バックアップを読み込む | **残す**（§4-1 が全教室へ昇格するまでは室長の唯一の復元手段） |

- 復元は「この教室だけ」に効き、他教室に影響しない（開発者画面のサーバー復元は教室選択モーダルで選んだ教室**だけ**を
  明示指定して保存し、他教室ドキュメントには一切書き込まない）。
- **復元時は確認モーダルで「元に戻せません」と警告してから実行。**
  - **【2026-07-04 確定・オーナー確認済み／C3】** この警告必須はそのまま維持する。監査時点では教室単位 JSON 読み込み・
    開発用教室への他教室読込には確認（上書き警告）があるが、**開発者画面のサーバーバックアップ復元モーダルには
    不可逆警告文言が無い**ため、実装側を本仕様に合わせて「復元すると選択教室の現在データは上書きされ、元に戻せません」を
    追加する（実装＋回帰テストは主セッションで対応）。

### 4-1. 室長による自教室のサーバーバックアップ復元 — 2026-09-18 オーナー確定（同日改定: 確認モーダル方式・直近3日）

オーナー要望「各校舎の室長が、15分毎のバックアップを自分の操作で自教室だけ復元できるように。復元にはパスワード要求を」。
2026-06-10 の「一般教室の室長への開放は見送り」（§7・§末尾）を、次の条件つきで改定する。

| 論点 | 確定 |
|------|------|
| 確定方法 | **画面へ読込 → 室長が「保存」で確定**。サーバーへ直接書く復元用 Cloud Function は**作らない**（既存の保存経路＝検証つき `saveClassroomSnapshot` だけを通す）。保存前は Undo（「直前の状態に戻す」）で取り消せる |
| 実行前の確認 | **画面中央の大きな確認モーダル**を必ず挟む。~~ログインパスワードの再認証~~ は v1.5.548 で入れたが、オーナー指示（2026-09-18）で v1.5.549 から**廃止**（パスワードは求めない） |

- **教室取り違え防止（2026-06-06 事故の再発防止）**
  - 復元元も復元先も**いま開いている教室**（`actingClassroomId`）。ハンドラは教室IDを引数に取らない。
  - 室長は「担当教室 ＝ 開いている教室 ＝ 復元対象」の 3 者一致が必須（`resolveManagerSelfRestoreGuard`）。
  - サーバー `downloadClassroomFromServerAutoBackup` は**自分の担当教室**（または開発者・検証用教室の室長）にしか返さない。
    これが権限境界。応答の教室IDが要求と違う／取得中に開いている教室が変わった場合は読み込まない。
  - 書き換えるのは自教室のスロットと編集 state だけ。自教室の復元なので共有トークンは剥がさない
    （剥がすのは他教室→検証用教室コピーだけ）。参照共有を断つディープクローンは行う。
- **確認モーダル（§4 の警告必須）**: 「この時点へ復元」でバックアップを取得したあと、画面中央に大きなモーダル
  （`role="alertdialog"`・幅 760px・文字 17px〜）を出し、室長が「この時点を読み込む」を押したときだけ読み込む。表示内容は
  `buildManagerSelfRestoreConfirmation` が権威:
  教室名と戻す時点／バックアップの規模（生徒数・講師数・テンプレコマ数＝取り違え防止・Feature B と同じ作法）／
  **「復元しても戻らないもの」**（必須・オーナー指示）／この教室だけ・未保存の編集は失われる・保存で確定・保存後は戻せない。
  - **言葉はアプリの画面の呼び名に合わせる**（オーナー指示「授業台帳という言葉はわかりにくい」）。内部名は出さない:
    `lectureSubmissions`→「QRで提出された講習の希望」／`parentMessages`→「保護者からの連絡」／
    `lessonLedgerDays`（授業台帳）→「生徒日程表の『通常授業履歴』に出る記録（出席・休み・振替の履歴）」／
    `operationEvents`（操作ログ）→「操作の記録（いつ・誰が・何を消したか）」。テストで内部語の混入を禁止している。
  - 取得（準備）と読込（確定操作）は別ハンドラ。準備段では画面のデータを一切書き換えない。確定時に、取得した教室IDを
    復元対象としてもう一度 3 者一致を照合する。確認待ちのデータは Undo と同じ 3 経路（教室を開き直す・ワークスペース読込・
    ログアウト）で破棄し、バックアップ/復元画面以外からは確定できない。
  - 在籍数台帳（`studentCountLedger`・請求用）も復元で戻らないが、室長の画面に出ない記録なので**モーダルには載せない**（意図的な省略）。
- **権限の位置づけ**: 権限境界はサーバーの担当教室判定。室長は元々自教室を保存できるので、確認モーダルは誤操作防止。
  3 日の窓も画面側の制限（自教室データの読み取りなのでサーバーでは絞らない）。
- **復元で戻らないもの**（§8 の保持方針どおり）: QR 講習提出（`lectureSubmissions`）・保護者連絡・操作ログ・授業台帳・在籍数台帳。
  古い時点へ戻すと「提出済みなのに盤面に未配置」になり得るが、起動時の自己修復（§7 B3）が効く。
  保護者用QRを復元時点より後に再発行していた場合、生徒データ内の写しトークンは古いものへ戻る（権威は `studentPortalTokens`。
  古い写しのQRは失効済みで開けない可能性があるので、該当生徒は QR を再発行する）。
  - **配布用盤面トークン（`classroomSettings.boardShareToken`）も復元時点の値へ戻る**。直近 7 日以内に再発行していた場合、

  8316830 / v1.5.300 が塞ぎ残した `openClassroom` 経路を同時に塞いだ。
- **開発者の入口が二重になる点はオーナー了承済み（2026-09-18）**: 開発者も「開いている教室 ＝ 復元対象」なら教室画面の

## 5. JSON バックアップ（書き出し／読み込み）

### 5-1. 教室単位（各教室画面）

- 書き出しは**開いている 1 教室分の“すべての状態・データ”**（テンプレート・設定・盤面・ストック等を含む）を 1 ファイルに。
- 読み込めば**完全復元**できること。読み込み時は確認（上書き警告）を出す。
- ファイル名は日本語＋日時入り。

### 5-2. 開発者画面：ワークスペース全体 — 2026-07-04 確定・オーナー確認済み（監査 B4）

- 教室単位（5-1）とは別に、**開発者画面のみ**「開発者バックアップ」として**ワークスペース全体
  （全教室・削除済み教室を含む）を1ファイルに書き出し／読み込み**できる。
- 読み込み時は**教室選択モーダル**で「復元する教室」を選ぶ（選んだ教室だけを復元し、選ばなかった教室は現状維持）。
  復元は選択教室のみを明示指定して保存し、他教室に影響しない（§4 と同じクロス汚染防止）。

### 5-3. 暗号化について — 2026-07-04 確定・オーナー確認済み（監査 B5）

- **JSON バックアップは平文（暗号化なし）**。読み込みにパスワードは不要。
- ローカル開発（Firebase 無効＝local モード）でのみ残っているパスワード入力プロンプトは**旧仕様の残骸**で、

### QR 提出反映の永続化非対称と起動時の自己修復 — 2026-07-04 確定・オーナー確認済み（監査 B3）

QR 提出（講師/生徒）を盤面へ反映する機能には**永続化経路の非対称**があり、これを前提に自己修復を設けている。

- `countSubmitted`（提出反映フラグ。`specialSessions` 内）は**手動保存しなくても** workspace 自動同期で永続化される。
- 一方、QR 提出による**盤面への講師名配置（boardState の weeks/desks）は手動保存（Cloud Function snapshot）でしか
  永続化されない**。
- そのため手動保存前にリロードすると盤面配置だけ揮発し、`countSubmitted=true` は残るため取り込みでスキップされ
  「提出したのに出席可能コマに名前が出ない」状態でスタックしうる。
- **対処（維持）**：起動時（教室ロード/リロード毎に1回）に `reconcileSubmittedTeacherPlacements` が
  「`countSubmitted=true` なのに未配置の講師」だけを**冪等に**再配置する。既に一部でも配置済みの講師は触らない
  （手動調整・部分削除を尊重）。全コマ外したい場合は登録解除で対応する設計と整合。

### 8-1a. 復元前の安全スナップショット（incident backup）— 2026-09-04 オーナー確定で 90 日保持へ

`downloadServerAutoBackup`・`prepareServerAutoBackupRestore`（＝復元の直前）で、全教室ぶんのワークスペーススナップショットを
`workspace-incident-backups/{workspaceKey}/` へ書き出している（2026-10-29 から `{reason}-{時刻}/` のフォルダに教室ごとの gzip＋目次・§10-3。それ以前は 1 本の JSON）。復元をやり直すための最後の砦。
ローカル同期フォルダの経路（`purpose: 'local-sync'`）では書かない（§10-5・Q8）。

**従来は自動削除が無く**、本番に 3,978 本＝46.8GB が残置されていた（うち 3,943 本が 2026 年 5 月に集中。
検証で復元ダウンロードを反復すると 1 回ごとに数十 MB が積み上がるため）。当時の Cloud Storage 請求の
ほぼ全額がこの残置分だった。

- 保持は **90 日**（`WORKSPACE_INCIDENT_BACKUP_RETENTION_DAYS`）。自動バックアップ側が日次 400 日を
  保持しているので、こちらは「直近の復元操作をやり直せる」期間があれば足りるという判断。
- 作成時刻は GCS オブジェクトの `timeCreated` を正とする（ファイル名の解析には頼らない）。
  **作成時刻が読めないもの・未来日時のものは削除しない**（日付が読めないものを消すと事故になる）。
- 掃除は `cleanupOldSaveAttempts`（cron `30 3 * * *`）の同じ巡回で行う。**Firestore 側の巡回より先**に、
  **独立した時間予算**（90 秒）で走らせる。後ろに置いて予算を共有すると、Firestore 側が使い切った晩は
  1 ページだけ見て打ち切り、翌晩もまた 1 ページ目から読み直すため、滞留分が永久に減らない。
- 初回の削除対象は実測済み（2026-09-04 時点・読み取り専用で確認）: **3,963 本 46.31GB を削除、15 本 0.45GB を保持**。
- バケットは**ソフト削除 7 日**が有効。削除しても 7 日間は復旧でき、その間は容量課金も残る
  （「削除したのに請求が下がらない」と誤判定しないこと）。
- 消さずに対象をログ出力するだけの空実行は環境変数 `INCIDENT_BACKUP_PRUNE_DRY_RUN=1` で有効化する。

### 8-1b. 操作ログ（`operationEvents`）— 2026-09-04 新設・オーナー確定

「未消化振替が減った／消えた」という問い合わせに答えるための**監査記録**。従来は 15 分毎の自動バックアップ（#7）を

  （件数を抑え、問い合わせに必要な情報だけ残す）。種別の正本は `functions/src/operationEvents.ts` の

### 8-2. 自動バックアップの段階間引き（#7・#8 共通）

生成は **15 分ごとの 1 本**に一本化し、保持は**保存時刻の経過時間**だけで判定する（生成種別に依存しない）。

| 経過時間 | 残す粒度 |
|---------|---------|
| 0〜24 時間 | 15 分刻み（全保持） |
| 24〜72 時間 | JST 毎時 0 分のみ（実質毎時） |
| 72 時間〜400 日 | JST 3:00 のみ（実質日次） |
| 400 日超 | 削除 |

- 定常状態の保持本数は概算 96＋48＋397 ≒ **540 本**（静音帯を引くと 73＋48＋397 ≒ 520 本。2026-09-04 に日次を 7 日→400 日へ延長）。容量（2026-10-28 実測・main 4 教室）:
  旧形式は非圧縮 1 本 31.7MB で定常約 16GB、教室別形式（§10・gzip）は 1 時点 約 3MB で約 1.6GB。Google Drive はどちらも gzip で約 1.6GB。
- **Google Drive の復元**: ミラーは `.json.gz`。アプリの「バックアップを読み込む」は gzip のマジックバイトで判定して
  ブラウザ内で解凍する（`src/utils/backupFileText.ts`）ので、解凍せずそのまま取り込める。gzip は可逆で、
  解凍結果は Storage の非圧縮 JSON とバイト単位で同一（往復テストで固定）。
- **静音時間帯（JST 3:15〜8:45）は生成を休止**して取得回数を抑える。ただし**日次アンカーの 3:00 は必ず取得**する
  （取らないと 72 時間〜400 日帯が丸ごと存在しなくなる）。
- Google Drive 側の削除は Drive API の `DELETE /files/{id}`＝**ゴミ箱を経由しない完全削除**。「Drive のゴミ箱から拾う」はできない。
- Drive の間引き対象は「**設定フォルダ内・`trashed=false`・`appProperties.workspaceKey` 付き**」のファイルのみ。
  手動で別フォルダへコピーしたものは間引かれず残る（長期保管したい場合の逃げ道）。

### 8-3. この保持設計の帰結（運用上の約束）

- **「その日の教室データを丸ごと当時の状態に戻す」は、日次（JST 3:00 時点）なら 400 日、15 分刻みなら 24 時間、毎時なら 72 時間が限界。**
  400 日は 2026-09-04 の延長以降に積み上がる分で、それ以前へは遡れない。それより前の誤操作はバックアップ復元では取り返せない。
  Google Drive 同期は**冗長化**（Web アプリを開かなくても JSON が残る／Firebase 障害時に手元にある）が目的であり、
  **長期アーカイブではない**。
- 一方で **「いつ誰が出席したか」（出欠）と講習の提出実績は無期限で残る**（#1・#5）。日々の実績照会に
  バックアップ復元は不要。
- **過去の在籍数（退塾済みを含む当時の人数）は 2026-08-15 以降のみ確定値**（#6）。それ以前は現名簿からのライブ計算＝
  当時と一致しない可能性がある。台帳が導入されたのはこの穴を塞ぐため。

### 8-4. 変更時の手順（厳守）

保持期間は**ユーザーへの約束**であり、コードの都合で黙って変えてよい数値ではない。

- 期間を変えるときは **(1) 本節の更新 (2) 定数のスペックロックテストの更新 (3) `CHANGELOG.md` への記載**を
  **同じコミット**で行う。テストは `functions/src/workspaceBackupSchedule.test.ts` および
  `src/components/schedule-board/boardWeekTrim.test.ts` の「保持期間のスペックロック」節。
- 特に **#1（手動編集を含む週は無期限）を弱めない**。`weekHasManualBoardData` の判定を1つでも落とすと、
  出欠・振替・メモを持つ過去週が静かに消える（データ消失＝最悪の回帰）。
- **#7 と #8 は同じ段階間引きを共有している。** 2026-09-04 に**意図的な非対称**を 1 つ入れた: Drive は gzip
  （`.json.gz`）でミラーし、旧来の非圧縮 `.json` だけは 7 日で間引く（`shouldKeepGoogleDriveBackupByName`・Drive 15GB 上限対策）。
  これ以外の「Drive だけ長く残す」等の非対称化は、意図的な分岐として
  本節に明記してから実装する。


## 9. 週単位の分割保存（教室データの恒久対策）— 2026-10-27 オーナー確定（方式・§9-15 の 6 論点とも）・段階 0〜B 実装済み（B＝サーバーが分割して書く・2026-10-28 v1.5.654・切り替えは開発用教室から）・C 以降未実装

> **方式（目次＋部品・変わった部品だけ保存）はオーナー採用済み**（2026-10-27「その順で進めて」）。
> 本章はそれを実装できる粒度へ補完したもの。**§9-15 の 6 論点は 2026-10-27 にオーナー確定**（すべて推奨案）。
> 残る【暫定】は速度・時間の目標値（AC-7・AC-8・AC-23）だけで、staging の本番サイズの実測で確定する（オーナー判断ではない）。

### 9-1. 背景（確定事実・2026-10-27）

- 教室データは 1 文書 `workspaces/{ws}/classroomSnapshots/{classroomId}` に gzip＋base64（`compressedData`）でまるごと入っている。
  日大前校がこの文書の上限 1MiB（1,048,576 バイト）に達し、10/26 17:58〜21:15 と 10/27 14:46 以降の保存が全部拒否された。
- つなぎ（v1.5.646）: 圧縮 level 9・容量超過/書き込み失敗の記録とメール・使用率 85% 超の通知。余裕は約 56KB（2〜4 週）しかなく、
  12 月の冬期講習で週が重くなるため、**恒久対策は冬期講習の前に本番へ出す**。
- 日大前校の中身（非圧縮 8,345,360 バイト）: `boardState.weeks` が 7.35MB（46 週＝2026-05-11〜2027-03-29・1 週 35 コマ。
  過去週 110〜415KB〔講習週が重い〕・未来週 約 105KB）。週以外は `specialSessions` 405KB・`classroomSettings` 162KB・
  `suppressedRegularLessonOccurrences` 154KB・`regularLessons` 65KB・`scheduleCountAdjustments` 62KB・`students` 26KB・
  `teachers` 14KB・`autoAssignRules` 10KB ほか。
- 出欠のある過去週は消せない（§8-1 #1・`weekHasManualBoardData`）ので、データは時間とともに増え続ける。保存は毎回 8MB を送り、15〜25 秒かかる。

### 9-2. 変えないもの（この章の前提・巻き戻し禁止）

### 9-3. 保存形式（目次＋部品）

#### 9-3-1. 文書の置き場所

| 文書 | パス | 役割 |
|------|------|------|
| **目次**（manifest） | `workspaces/{ws}/classroomSnapshots/{classroomId}`（**既存の文書をそのまま使う**・パス不変） | 版数・保存時刻・部品の一覧（文書 ID とハッシュ）。中身は持たない |
| **部品**（part） | `workspaces/{ws}/classroomSnapshots/{classroomId}/snapshotParts/{partDocId}` | 中身。1 部品 1 文書・gzip＋base64 |

- サブコレクション名は `snapshotParts`。旧「分割保存」の名残 `chunks` / `parts` / `boardWeeks` とは**別名にする**（旧読み取り経路との取り違え防止）。
- 部品は教室の目次の下にしか置かない（教室分離はパスで担保・INV-08）。

#### 9-3-2. 部品の分け方（オーナー確定 2026-10-27・§9-15 Q1＝B）

| 部品 | キー | 中身 | 大きさ（日大前校・推計） | 変わる契機 |
|------|------|------|----------------------|-----------|
| 管理データ | `core` | `boardState` と `screen` を除いた教室データ全部（`classroomSettings`・`managers`・`teachers`・`students`・`regularLessons`・`groupLessons`・`specialSessions`・`autoAssignRules`・`pairConstraints`・**未知のフィールドも含む**） | 非圧縮 約 0.7MB／保存 約 85KB | 基本データ・設定・講習の編集、QR 提出のマージ |
| 盤面の週以外 | `board` | `boardState` から `weeks` と画面状態（下記）を除いた全部（`suppressedRegularLessonOccurrences`・`scheduleCountAdjustments`・`manualMakeupAdjustments`・`suppressedMakeupOrigins`・手動ストック・`groupClassEntries`・`templatePendingDesks`・**未知のフィールドも含む**） | 非圧縮 約 0.3MB／保存 約 36KB | 盤面の多くの操作 |
| 週 | `week:{週キー}` | `boardState.weeks` の 1 要素（コマの配列） | 非圧縮 105〜415KB／保存 約 12〜50KB | その週の編集・テンプレ反映 |
| 画面状態 | （部品にせず**目次に平文で持つ**＝`ui`） | `screen` と `boardState` の `weekIndex`・`selectedCellId`・`selectedDeskIndex`・`isLectureStockOpen`・`isMakeupStockOpen`・`studentScheduleRange`・`teacherScheduleRange`（**この固定リストだけ**。未知のフィールドは `ui` に入れない） | 数百バイト | クリック・画面移動のたび |

- 大きさは全体の圧縮率（8.35MB → 約 0.99MB）からの**推計**。実測は §9-13 の staging 計測で確定する。
- 合意時の案は「週以外を 1 文書（core）」。それだと画面状態（選択中のコマ）が core に入り、**ほぼ毎回の保存で core（約 85〜120KB）を送り直す**ことになるため、
  管理データと盤面の週以外を分け、画面状態を目次へ出す（§9-15 Q1 でオーナー確定）。
- `boardState` が `null` の教室は `board` も週も無し（目次の `hasBoardState: false`）。

#### 9-3-3. 週キー

- 週キー＝その週のコマの `dateKey` の最小値（`YYYY-MM-DD`・`boardWeekTrim.ts` `weekDateRange` と同じ規則）。コマが無い・日付が取れない週は `nodate`。
- 同じキーが 2 回以上出たら、配列で 2 回目以降を `~2`・`~3`…とする（例 `2026-05-11~2`）。キーは目次の中で一意。
- **週の順番は目次の `weeks` 配列の順が正**。組み立てで日付順に並べ直さない（`weekIndex` は配列の位置を指すため）。
- 週キーの算出・分割・組み立ては 1 つの純関数モジュール（§9-5-1）だけが行う。

#### 9-3-4. 目次の項目

| フィールド | 内容 |
|-----------|------|
| `schemaVersion` | 1（従来どおり） |
| `storageFormat` | `'weekly-parts'`。**この印が無い文書は旧形式** |
| `storageFormatVersion` | 1 |
| `version` | A1 の版数（従来どおり保存ごとに +1・QR マージでは据え置き） |
| `savedAt` / `updatedAt` / `updatedBy` | 従来と同じ名前・同じ意味（メタだけを読む既存処理＝QR 提出通知の基準時刻・tools の `mask` 読みを壊さない） |
| `saveId` | この目次を作った保存の saveId（冪等リプレイの判定・§9-4-6）。QR マージでは変えない |
| `compositeHash` | 全体ハッシュ（§9-3-6） |
| `managementCount` | 管理データ件数（`countClassroomManagementData` の値。空データ上書き拒否に使う） |
| `dataByteLength` | 組み立て後の JSON の総バイト（非圧縮・参考値） |
| `hasBoardState` | `boardState` が `null` でないか |
| `ui` | 画面状態（§9-3-2） |
| `parts` | `core` と `board` の部品情報（`board` は `hasBoardState: false` なら無し） |
| `weeks` | `[{ key, ...部品情報 }]`（順番＝`boardState.weeks` の順） |
| `lastWriter` | `'save'` / `'qr-submission'` / `'provision'` |

部品情報＝`{ docId, hash, rawBytes, storedBytes }`。目次には旧形式の `data` / `dataEncoding` / `compressedData` を**書かない**（目次は `set` で丸ごと置き換え、旧フィールドを残さない）。
目次の大きさは 46 週で約 10KB、10 年分（約 520 週）でも約 100KB。

#### 9-3-5. 部品文書の項目と ID

- 項目: `classroomId`・`kind`（`core` / `board` / `week`）・`key`・`hash`・`encoding: 'gzip-base64'`・`compressedData`・`rawByteLength`・
  `createdAt`（サーバー時刻）・`createdBy`（saveId または `qr-…`）・`createdForVersion`・`gcMarkedAt`（掃除の印・§9-9）。
- 文書 ID＝`{kind}~{key}~v{版数}~{書き手 ID 先頭 12 文字}`（例 `week~2026-05-11~v1234~a1b2c3d4e5f6`、core は key を `-`）。
  書き手 ID は保存なら saveId、QR マージなら `qr{ミリ秒}{乱数4桁}`。
- ★**部品は一度書いたら書き換えない（不変）**。中身が変われば必ず**新しい ID の文書**を作る。同じ ID への 2 回目の書き込みは同一 saveId の再送だけ（同じ内容）。
- 圧縮はサーバーが level 9（`SNAPSHOT_GZIP_LEVEL`）で行う。

#### 9-3-6. ハッシュの定義

- **部品ハッシュ**＝SHA-256（16 進）of `stableStringify(sanitizeForFirestore(部品の中身))`（`stableStringify` は既存のキー並べ替え版）。
  週の中身はコマの配列（旧 `{ cells }` 形は配列に直してから）。
- **全体ハッシュ（`compositeHash`）**＝SHA-256 of `stableStringify({ f: 'weekly-parts-v1', ui, hasBoardState, core: 部品ハッシュ, board: 部品ハッシュ | null, weeks: [[週キー, 部品ハッシュ], …] })`。
- 合意時の「全体の `payloadHash`」は、変わっていない部品まで全部読んで組み立てないと計算できない（毎回 8MB を読むことになり分割の意味が薄れる）ため、
  **部品ハッシュの一覧から作る全体ハッシュに置き換える**。読み戻し検証の強さは同等（各部品は書いた直後に中身から照合する）。
  `saveAttempts.payloadHash` には分割形式では全体ハッシュを入れ、`hashScheme: 'parts-v1'` を併記する（旧形式の値と混同しない）。
- 正しさは**サーバーが計算したハッシュだけ**に依存させる。クライアントのハッシュは「どれを送るか」の判断にしか使わない
  （クライアントとサーバーで計算が食い違っても、余計に送るだけで保存内容は正しい）。

#### 9-3-7. 大きさの上限と監視

| 対象 | 上限 | 通知（開発者メール・教室ごと 1 日 1 通） |
|------|------|------------------|
| 部品 1 文書・目次 | 1MiB（`FIRESTORE_DOCUMENT_MAX_BYTES`） | 85% 以上（既存の `capacity-warning` を**全文書に**適用） |
| `core`・`board` | 同上 | **50%（512KiB）以上で「部品の追加分割（第 2 段）着手の合図」通知**（`split-capacity-notice`） |
| 1 回の書き込み（トランザクション） | 書き込み 400 件・8MiB（Firestore の 500 件・10MiB の 8 割） | 50%（200 件・5MiB）以上 |

- `core` の上限見込み: 非圧縮 約 8.8MB で 1MiB に届く。現在 約 0.7MB。`specialSessions` は講習ごとに増える（1 講習の増分は**要実測**。仮に 200KB・年 3 講習なら年 0.6MB）ため、
  **当面（数年単位）は分割不要**と判断する。50% 通知が来たら、`specialSessions` を講習ごとの部品（`session:{id}`）に分ける第 2 段を起票する。
  目次の形式は部品の種類を足せる作りにしておく（ただし種類を足すときも §9-7 と同じく「先に読める版を出す」2 段で入れる）。
- `board` も `suppressedRegularLessonOccurrences` が増え続けるので同じ 50% 通知の対象。
- 1 週の最大は講習週で非圧縮 415KB→保存 約 50KB。週の部品が上限に届く心配は当面無い（85% 通知は効かせる）。
- 書き込み件数の見込み: 普段の保存 3〜5 件、テンプレ保存（未来 26 週）約 30 件、全量（移行・復元）約 50 件。年 52 週増えるので、全量が 400 件に届くのは**約 7 年後**。

### 9-4. 保存

#### 9-4-1. リクエストの形

- **新しい形**（分割形式を読める版のクライアントが、分割形式の教室へ送る）: `payload` の代わりに `partsSave` を送る。
  - `format: 'weekly-parts-v1'`・`ui`・`hasBoardState`・`weekKeys`（全週キーを順番どおり）
  - `sent`: 送る部品 `{ [部品キー]: { encoding: 'gzip-base64' | 'json', data } }`（部品キーは `core` / `board` / `week:{週キー}`）
  - `unchanged`: 送らない部品 `{ [部品キー]: そのタブが知っているサーバー側のハッシュ }`
  - `baseVersion`・`saveId`・`savedAt`・`operationEvents`・`lessonLedger`・`operationTrace`・`client` は従来どおり
  - 部品キーの集合（`core`・`hasBoardState` なら `board`・全週）が `sent` と `unchanged` に**ちょうど 1 回ずつ**現れること。過不足は `invalid-argument`。
  - 送る部品は**クライアントで gzip** する（`CompressionStream`。無い環境は `json` のまま）。サーバーは解凍・JSON 解析・sanitize してからハッシュを計算し、自分で level 9 に圧縮し直して保存する。
- **従来の形**（`payload` に教室データ全体）も**受け付け続ける**。サーバーが共有の分割関数で部品に分け、「全部品を送った」新しい形として同じ処理に流す。

#### 9-4-2. 送る部品の決め方（クライアント）

- 教室ごとの台帳（`classroomSnapshotParts`・`classroomSnapshotVersions` と同じ置き方）に「サーバーの目次の部品ハッシュ」を持つ。
  - 記録するのは**読込直後（目次から）と保存成功直後（応答から）だけ**。
  - **読込・教室を開く／切り替え・ワークスペース読込・ログアウトで、その教室の台帳を消す**（他教室の台帳と比べない・INV-08）。
- 保存のたび、手元の教室データを共有の分割関数で部品に分け、**各部品のハッシュを中身から毎回計算**し、台帳と違う部品だけ `sent` に入れる。
  - ★**参照の同一性（前回と同じオブジェクトだから変わっていない）で計算を省かない**。省いた判定が外れると、変えた週が送られず、
    サーバーの照合でも検出できないまま「最新データ」になる（INV-02 違反の型）。計算時間は §9-12 の数値で縛る。

#### 9-4-3. 全量送信へ切り替える条件

「全量送信」＝全部品を `sent` に入れる（サーバーは中身が同じ部品を書かずに再利用するので、書き込みは変わった部品だけのまま）。

| 条件 | 送り方 |
|------|-------|
| 台帳が無い（旧形式の教室を読んだ・読込直後に記録できなかった・台帳を消した後の最初の保存） | 全量 |
| 復元（§4-1）・JSON 読込（§5）・開発者の復元／Feature B 読込・初期設定のリセットの直後 | 全量（安全側。台帳を消す） |
| サーバーが `PARTS_BASE_MISMATCH`（§9-4-7）を返した | 1 回目: 返されたキーの部品を足して同じ saveId で再送。2 回目も同じなら全量で 1 回。それでも失敗したら通常の失敗処理（§2） |
| ハッシュ計算ができない（`crypto.subtle` が無い等） | 従来の形（`payload` 全体） |
| サーバーが `PARTS_FORMAT_UNSUPPORTED` を返した | 従来の形（`payload` 全体） |
| 版数衝突（STALE） | 送らない。従来どおり同期停止→再読み込み（再読み込みで台帳は作り直される） |

#### 9-4-4. サーバーの処理順（`saveClassroomSnapshotFromCallable`）

1. 引数検査・権限（`requireClassroomAccessMember`・開発用教室限定の分岐）— 従来どおり。
2. 送られた部品を解凍→解析→sanitize→ハッシュ計算。週は中身から出した週キー（`~n` を除いた日付部分）が申告のキーと合うこと。合わなければ `invalid-argument`（開発者へ `parts-invalid` 通知）。
3. 全体ハッシュを計算（送られた部品はサーバー計算値、送られていない部品は申告値）。
4. `saveAttempts/{saveId}` の照合（従来どおり）: 同じ saveId で全体ハッシュが違えば `already-exists`、検証済みならリプレイとして結果を返す（ログ類も再送）。
5. 教室の存在確認 → `saveAttempts` に `started` を記録。
6. **トランザクション**（ここで初めて目次を読む）:
   1. 目次を `transaction.get`。**旧形式なら「本体から作った仮想の目次」**（部品は未書き込み・ハッシュは本体の中身から計算）として扱う（初回移行・1 回だけ解凍する）。
   2. 目次の `saveId` がこの saveId なら、既に確定済みの再送なので**何も書かずに抜けて 7 へ**。
   3. A1: `resolveOptimisticVersionDecision`（`isReplay` は **2. のときだけ true**・§9-4-6）。不一致は STALE で中止。
   4. `unchanged` の申告ハッシュを目次と照合。違うキーがあれば `PARTS_BASE_MISMATCH`（キーの一覧つき）で中止（何も書かない）。
   5. `sent` のうち目次と同じハッシュの部品は既存の文書を再利用（書かない）。旧形式の仮想目次では「再利用」でも中身を旧本体から書く。
   6. 空データ上書き拒否: `core` が変わるときだけ新しい `core` の管理データ件数を数え、0 件かつ前の `managementCount` が 1 件以上なら拒否。
   7. 書き込み件数・バイトの上限判定（§9-4-5）。超えれば容量超過（`too-large`）で中止。
   8. 新しい部品を `create`（新 ID）、目次を `set`（版数 +1・`saveId`・`savedAt`・`updatedBy`・`compositeHash`・`managementCount`・部品一覧）。
   - ★トランザクションの中では**判定と書き込みだけ**。メール・`saveAttempts` の記録は確定後に外で行う（トランザクションは再実行されうるため）。
7. **読み戻し検証**: 目次を読み直し（`saveId`・`version`・`compositeHash` が一致）、**この保存で書いた部品を全部**読み直して解凍・ハッシュ照合する
   （書いていない部品は不変なので読み直さない）。
   - 不一致なら、**目次を直前の内容へ戻す**（トランザクション・目次の `saveId` がこの saveId のときだけ）→ `verification-failed` を記録・通知 → `internal`。
     従来は壊れた文書が生きたまま残ったので、ここは強化。
8. `verified` を記録 → 操作ログ・授業台帳・操作痕跡（K-6）→ 容量通知（最後・K-5）。
9. 応答: `version`・`compositeHash`・`partHashes`（全部品キー→ハッシュ）・`writtenPartKeys`・`writeMode`（`cloud-function-parts`）・`dataByteLength`。リプレイの応答も同じ項目を目次から返す。

#### 9-4-5. トランザクションの上限と超えたとき

- 部品の書き込みと目次の切り替えは**1 トランザクション**（合意どおり）。上限は書き込み 400 件・8MiB（§9-3-7）。
- 超えたときは**分けて書かない**（原子性が崩れる）。容量超過として理由つきで拒否し、`too-large` を記録・開発者へ通知する（K-5 と同じ扱い・利用者には容量超過の専用案内）。
- 現在の見込み（全量でも約 50 件・約 1.2MB）では起きない。50% 通知（§9-3-7）が来たら、次の**第 2 段**を実装する:
  「部品を先に別バッチで書き（どの目次からも参照されないので誰にも見えない）、最後に目次だけをトランザクションで切り替える（切り替え時に新しい部品の存在を確認）」。
  見える状態は目次の切り替えだけで決まるので、この方式でも原子性は保たれる。
- テンプレ保存・丸ごと振替など多くの週が一度に変わる操作も、普段の保存と同じ 1 トランザクション（テンプレ保存で約 30 件）。

#### 9-4-6. A1・3 層防御の引き継ぎ（§1・§2 の具体化）

| 守り | 分割形式での実装 |
|------|----------------|
| A1 版数照合 | 目次の `version` を**トランザクション内で**照合する（従来は読む→書くの間に隙があった。ここは強化） |
| 冪等リプレイ | (a) `saveAttempts` が検証済み→結果を返す（従来どおり）。(b) 目次の `saveId` がこの saveId→確定済みとして読み戻し検証だけして返す。**「記録はあるが未検証」だけを理由に版数照合を飛ばさない**（従来の `isReplay` は (b) の場合だけ） |
| 空データ上書き拒否 | 前回の件数は目次の `managementCount`（旧形式なら 1 回だけ解凍して数える）。`core` を変えない保存は件数が変わらないので照合不要 |
| 読み戻し検証 | §9-4-4 の 7。書いた部品の全部と目次。失敗時は目次を戻す |
| 容量超過の記録 | 部品・目次・トランザクションのどれが上限かを `detail` に残す（K-5 の文言・マーカーは不変） |

#### 9-4-7. 失敗の種類（追加分）

| 種類 | 返し方 | クライアント | 開発者通知 |
|------|-------|------------|----------|
| `PARTS_BASE_MISMATCH` | `failed-precondition`＋先頭マーカー＋`details.keys` | 画面に出さず §9-4-3 の手順で自動再送（一時エラーの 3 回再試行とは別に数える） | しない（QR マージの直後などに普通に起きる）。`saveAttempts.status = 'base-mismatch'` |
| `PARTS_FORMAT_UNSUPPORTED` | `failed-precondition`＋マーカー | 従来の形で再送 | しない |
| `CLIENT_TOO_OLD`（§9-7-3） | `failed-precondition`＋マーカー | 旧版は通常の失敗処理（JSON 自動退避＋再ログイン案内） | する（`client-too-old`） |
| 部品の不正 | `invalid-argument` | 通常の失敗処理 | する（`parts-invalid`） |
| 容量超過・書き込み失敗・読み戻し失敗・空データ・STALE | 従来どおり | 従来どおり | 従来どおり |

### 9-5. 読み込み（組み立て）

#### 9-5-1. 共有の純関数（1 か所）

- 分割・組み立て・週キー・正規化・`stableStringify`・全体ハッシュの入力作成・目次の検査は、**自己完結の純関数モジュール 1 つ**
  （置き場所は `src/utils/classroomSnapshotParts.ts`〔仮〕）に書き、`functions/scripts/sync-shared.mjs` で `functions/src/generated/` へ複製する
  （`parentSchedule.ts` と同じ作法・import 0 行）。ハッシュ関数（ブラウザ `crypto.subtle`／Node `crypto`）と Firestore の読み書きは外から渡す。
- ★**同一性の約束**: どんな教室データ `P` でも、`組み立て(分割(P))` は今日の読み取り結果 `deserializeSnapshotPayload(sanitizeForFirestore(P))` と
  `stableStringify` が一致する（週は配列形・`boardState: null` は null のまま・未知のフィールドも残る・`ui` の「無い」と「null」を区別して残す）。
  これにより既存の読み手（盤面・日程表・バックアップ・保護者ページ…）は**中身の形が今日と同じものを受け取り、無改修で動く**。

#### 9-5-2. 読み取りの一貫性

- 読み方は「目次を読む → 目次が指す文書 ID の部品を読む」。部品は不変で、参照が外れても最低 3 日残る（§9-9）ので、
  **読み取り中に目次が切り替わっても、読み始めた時点の一式がそろう**（再試行は不要）。
- 部品が見つからない・ハッシュが合わないときは、**目次を 1 回だけ読み直して**やり直す。それでも欠けていれば**組み立て失敗**（例外）とする。
- 読むたびに部品ハッシュを照合する（中身の破損を検出するため。8MB で数十ミリ秒）。

#### 9-5-3. ★組み立て失敗は「空」にしない（fail-closed・INV-14）

- 目次が存在するのに組み立てられないとき、**`null`（＝空の教室）を返さない**。必ず例外にする。
  - 現行のクライアントは読めない形式を `null`→`createEmptyClassroomPayload()`（空の教室）にしている。空や一部欠けの教室を表示して保存すると、
    欠けた週・データがそのまま消える（データ消失）。分割形式でこの道を作らない。
- **クライアント**: その教室は「読み込めませんでした。画面を再読み込みしてください。直らなければ開発者へ連絡してください」と表示し、盤面を出さず、**その教室の保存を止める**。
- **サーバー**: 呼び出し元ごとに次のとおり。
  - QR 提出のマージ: マージしない（提出は `lectureSubmissions` に残り、室長側は購読で反映＝現行の失敗時と同じ）。ログ＋開発者通知。
  - 自動バックアップ: その教室を**空で書かない**。その教室を除いて書き、要約に `missingClassroomIds` を残し、開発者へ `snapshot-assembly-failed` を通知
    （15 分毎のバックアップが整合監視を兼ねる）。
  - 直前ロールバック・版履歴（トリガ）: 書かずにログ＋通知（直前ロールバックの失敗は従来どおり投げ直す）。
  - 保護者ページ・在籍数台帳・その他: 従来の「読めない」扱いの文言のままエラーにする（空データで計算しない）。
- 文書が**存在しない**ときだけ従来どおり `null`（新しい教室）。

#### 9-5-4. 置き換える読み手（2026-10-27 時点・実装時に再 grep して漏れなく）

- サーバー: `readStoredSnapshotPayload` は同期関数で部品を読めないため、**非同期の組み立て関数**（例 `readClassroomSnapshotPayload(doc, { ref, transaction? })`）へ全呼び出し箇所を置き換える。
  対象: 直前ロールバック（before/after）・版履歴（after）・`loadWorkspaceSnapshot` 系（自動バックアップ・復元前の安全スナップショット・開発者ダウンロード）・
  在籍数台帳・`lectureSubmissionApi` のマージ・保護者ページ（日程・生徒の実在確認）・空データ上書き拒否（旧形式のときだけ）・保存の読み戻し。
  - トランザクション内で読むときは**目次だけ** `transaction.get`。部品は不変なのでトランザクション外で読んでよい。
  - 部品の取得は `getAll`（サーバー）／並列 `getDoc`（クライアント）。サブコレクション全体の一覧取得はしない（掃除待ちの旧版まで読んでしまう）。
- クライアント: `readFirebaseSnapshotPayload` に分割形式の枝を足す（旧 3 形式の枝は残す）。読込時に目次の部品ハッシュを §9-4-2 の台帳へ記録。
- tools: 現行で Firestore の教室スナップショット本体を直接解くツールは無い（`snapshot-diff.mjs` は Storage の版履歴を読む・要確認）。
  直接読むツールを足すときは共有の組み立て関数を使う。

### 9-6. 同じ文書へ書く他の経路（兄弟経路）

| 経路 | 分割形式での扱い |

### 9-7. 移行（段階・後方互換）

#### 9-7-1. 段階

| 段階 | 出すもの | 書く形式 | 次へ進む条件 |
|------|---------|---------|------------|
| A | **読める版**: サーバーの組み立て関数（全呼び出し箇所）・クライアントの分割形式の読み取り（fail-closed）・`snapshotParts` のルール | 旧形式のまま | Functions → ルール → Hosting の順に反映済み。staging で「分割形式の目次を手で作って読める」こと。**各教室の直近の保存がすべて段階 A 以降の版から来ている**こと（`saveAttempts.appVersion` で確認） |
| B | **サーバーが分割して書く**: 保存（従来の形の全量を受けてサーバーで分割）・トランザクション・読み戻しと目次の巻き戻し・QR マージ・トリガ・バックアップの失敗処理・掃除・旧版の拒否（§9-7-3）。サーバー側の機能フラグ（`weeklySplitSnapshotStorage`・`functions/src/snapshotStorageFormat.ts`・基本スコープ＋教室指定＋会社既定）。**2026-10-28 実装（v1.5.654・§9-17）** | フラグ ON の教室は最初の保存から分割形式 | ★**これで 1MiB の上限問題は解消する**（送信は 8MB のまま）。冬期講習前に日大前校まで反映する。切り替えの進み: 開発用教室（v1.5.654・移行と QR 取り込みを確認）→ **全教室（v1.5.656・オーナー指示 2026-10-28「staging は確認しなくていいので、問題なければ本番環境へ全教室展開して」＝§9-15 Q4 の staging・日大前校の段を省略）** |
| C | **差分送信**: クライアントの台帳・変化判定・gzip 送信・全量への切り替え | 同上 | 速度の目標（§9-12）を staging の本番サイズで満たす。**2026-10-28 オーナー判断で保留**（速さだけの改善。室長から保存の遅さ・回線の弱い場所での失敗の不満が出たら着手。教室数は再開条件にしない） |
| D | 監視の見直し・第 2 段（部品の先書き・`core` の分割）・過去週のアーカイブ（未決・§9-16） | — | 50% 通知・読み込み時間を見て判断。**2026-10-28 オーナー判断: 来年の講習期に保存時間・起動時間を実測してから判断** |

- 機能フラグは**書く形式の選択にだけ**使う（読むのはフラグに関係なく両形式）。クライアントは「読んだ文書が分割形式なら差分送信」とだけ判断するので、クライアント側のフラグは要らない。
  フラグの段階（開発用教室 → staging → 教室指定 → 全教室）は `developmentStatusLedger.ts` に載せる（CLAUDE.md の規則）。
- ★**一方通行**: 分割形式になった教室は、フラグを OFF にしても**旧形式へ戻さない**（日大前校は旧形式に収まらない）。フラグ OFF は「新しく移す教室を止める」だけ。
- 段階 B と C は分けて出す（オーナー確定 2026-10-27・§9-15 Q6＝A）。B を先に出し、C は後から出す。期限（冬期講習前）に効くのは B。

#### 9-7-2. 旧形式の扱い（永久に読める）

- 旧形式の文書・Storage のバックアップ・版履歴・直前ロールバック・Drive の `.json.gz`・JSON バックアップは**読み続ける**（変換しない）。
- 旧形式の教室への保存は、段階 B のフラグ OFF なら従来どおり旧形式で書き、ON なら仮想の目次（§9-4-4 6-1）から全部品を書いて移る。
- 移行は「教室を開いて保存した時」に起きる。保存されない教室は旧形式のまま（それで問題ない）。

#### 9-7-3. 古いバンドルの端末

- 段階 A より前の版は分割形式を**読めず、空の教室として表示してしまう**（現行の読めない形式＝空）。起動時の `useAppVersionMonitor` が最新へ自動リロードするので、
  起きるのは「段階 B の切り替えをまたいで開きっぱなしのタブが、教室を読み直したとき」だけ。
- 対策（オーナー確定 2026-10-27・§9-15 Q2＝A）: 分割形式の教室への保存で、`client.appVersion` が段階 A の版より古い（または送られていない）ものは `CLIENT_TOO_OLD` で拒否する。
  実装（2026-10-28）では**分割形式へ移る保存（旧形式の教室のフラグ ON 後の最初の保存）にも適用**する（安全側・§9-17）。
  旧版の画面は通常の失敗処理（JSON 自動退避＋案内）になる。空の教室を読んだ古いタブが基本データを 1 件でも入れて保存すると
  空データ上書き拒否（0 件だけを止める）をすり抜けて教室を上書きしてしまうため、その道を塞ぐ。
- 切り替え前に、§9-7-1 の条件（直近の保存がすべて段階 A 以降の版）を確認し、室長へは「切り替え日に一度ハードリロード」を案内する（`safe-release`）。
- ★**ロールバックの制限**: 分割形式の教室が 1 つでもある間は、Hosting・Functions を**段階 A より前の版へ戻さない**（戻すと読めない）。
  実装時に `docs/runbooks/rollback.md` の A・B にこの制限を書き足す。

### 9-9. 旧版の部品の掃除と保持（§8 への追加）

- 掃除は `cleanupOldSaveAttempts`（cron `30 3 * * *`）の同じ巡回で、**独立した時間予算**（例 60 秒）で行う（§8-1a と同じ作法）。
- 規則（純関数 `resolveSnapshotPartGcActions` で固定）:
  1. 教室ごとに目次を読み、参照中の部品 ID の集合を作る。**目次が無い教室は何もしない**。
  2. `snapshotParts` を ID と `gcMarkedAt` だけ読む（`.select()`）。
  3. 参照されていない部品で印が無い → `gcMarkedAt = 今` を付ける（初回の発見）。
  4. 参照されていない部品で、印から **3 日**（`SNAPSHOT_PART_GC_GRACE_DAYS`・最低 1 日）以上たったもの → **目次を読み直して**まだ参照されていないことを確かめてから削除。
  5. 参照されている部品に印があれば消す（目次の巻き戻しで再び参照された場合）。
  6. 旧形式のサブコレクション（`chunks` / `parts` / `boardWeeks`）と `saveAttempts` 等には触れない。
- 部品は書き換えない・新しい保存は新しい ID しか参照しない・巻き戻しは直前の目次（数秒前まで参照していた部品）にしか戻らない、の 3 点で、
  参照中の部品を消す競合は起きない。
- 空実行は環境変数 `SNAPSHOT_PART_GC_DRY_RUN=1`。
- 実装（2026-10-28・`pruneSnapshotParts`）の補足: 旧形式の文書（目次でない）の教室は「参照中の部品なし」として扱う（読み戻し失敗で旧形式へ戻った移行の部品が残るため）。壊れた目次（検査に落ちる）の教室は触らない。目次は必要な項目だけ `select` で読む（旧形式の `compressedData` を読まない）。削除の直前に目次を読み直す（規則 4）。
- 保存の監査記録（`saveAttempts`）の 30 日・PITR の 7 日（§8-1 #16）は変えない（PITR は削除済みの部品も過去時点で読めるので、掃除の 3 日と両立する）。

### 9-12. 受け入れ条件

**形式・組み立て**
- AC-1 どんな教室データでも `組み立て(分割(P))` と現行の読み取り結果の `stableStringify` が一致する（空の盤面・`boardState: null`・日付の無い週・同じ開始日の週 2 つ・未知のフィールド・`ui` の無し/null・旧 `{cells}` 形を含むフィクスチャ、および日大前校の実データのコピー）。
- AC-2 週の順番を入れ替えた教室データは、組み立て後も同じ順番に戻る（日付順に並べ直さない）。
- AC-3 部品キーの算出は同じ入力で常に同じ結果。同じ開始日の 2 週目は `~2`。
- AC-4 部品・目次のどれも 1MiB を超えない。超える部品があれば保存は `too-large` で拒否され、`saveAttempts` に部品キーつきで残り、開発者へメールが届く。
- AC-5 `core` または `board` の保存サイズが 512KiB 以上の保存は成功し、開発者へ `split-capacity-notice` が 1 日 1 通届く。

**保存**
- AC-6 分割形式の教室で 1 週だけ編集して保存すると、送信は `board`（変わっていれば）とその週だけ、Firestore の書き込みは部品 2 件以下＋目次 1 件＋`saveAttempts` で、**リクエストの大きさは 300KB 以下**（日大前校サイズ）。
- AC-7 日大前校サイズで、普段の保存（1〜2 週の編集）は「保存」を押してから「最新データ」まで **5 秒以内**（staging・オーナーの PC 相当で 10 回の中央値）【暫定】。全量送信でも 30 秒以内に成功する。
- AC-8 手元の部品ハッシュの計算は日大前校サイズで 500 ミリ秒以内（同上）【暫定】。
- AC-9 テンプレ保存（未来 26 週が変わる）が 1 トランザクションで成功し、書き込み件数が `saveAttempts.writeCountInTx` に残る。
- AC-10 書き込み件数 400 件または 8MiB を超える保存は、何も書かずに `too-large` で拒否される（部品も目次も変わらない）。
- AC-11 別の端末が先に保存した教室へ古い版数で保存すると STALE で拒否され、部品は 1 件も増えない。
- AC-12 「`saveAttempts` は未検証で残っているが目次は前のまま」の再送は版数照合を受ける（照合を飛ばさない）。目次の `saveId` が同じ再送は書かずに成功を返す。
- AC-13 QR 提出のマージ後、室長の次の保存は `PARTS_BASE_MISMATCH` → `core` を足した自動再送で成功し、利用者には何も表示されない。マージで版数と `savedAt` は変わらない。
- AC-14 管理データ 0 件の `core` を送る保存は、前の `managementCount` が 1 件以上なら拒否される。`core` を送らない保存はこの照合で止まらない。
- AC-15（INV-14）読み戻しで部品のハッシュが合わないとき、目次は保存前の内容に戻り、`verification-failed` が記録され、利用者には従来の読み戻し失敗の文言が出る。
- AC-16 従来の形（`payload` 全体）の保存も分割形式で保存され、組み立てた結果が送った内容と一致する。
- AC-17 旧形式の教室の最初の保存で分割形式へ移り、直前ロールバック（Storage）には移行前の教室データ全体が残る。
- AC-18 分割形式の教室へ、段階 A より前の版（または版の無い）クライアントが保存すると `CLIENT_TOO_OLD` で拒否され、部品も目次も変わらない（§9-15 Q2）。

**読み込み**
- AC-19（INV-14）部品が 1 つ欠けた目次を読むと、クライアントはその教室を空で表示せず、案内を出して保存を止める。サーバーの読み手は例外にする（空の教室データで計算・保存しない）。
- AC-20 読み取りの途中で目次が切り替わっても、読み始めた時点の一式が組み立てられる（旧版の部品が残っているため）。
- AC-21（INV-14）自動バックアップは、組み立てに失敗した教室を空で書かず、`missingClassroomIds` に残して開発者へ通知する。他の教室は通常どおり書く。
- AC-22 版履歴（Storage）と直前ロールバックは、分割形式の教室でも教室データ全体の単一文書形式で書かれ、`tools/snapshot-diff.mjs` がそのまま読める。
- AC-23 日大前校サイズの読み込み（ログイン→盤面表示）は現行より 2 秒以上遅くならない【暫定】。

**ルール・掃除**
- AC-24 §9-8 のルールテスト 1〜7 が `npm run test:rules` で通る。
- AC-25 掃除は、参照中の部品・目次の無い教室の部品・旧形式のサブコレクションを消さない。参照が外れた部品は印から 3 日たつまで消さない。

**移行・運用**
- AC-26 段階 A の版は、旧形式 3 種と分割形式のどれも読める（クライアント）。サーバーは旧形式 2 種と分割形式を読める。
- AC-27 機能フラグ OFF の教室は旧形式のまま保存される。分割形式になった教室はフラグ OFF でも分割形式のまま保存される。
- AC-28 確認リスト（`verificationChecklist.ts`）・進行中テーマ台帳（`developmentStatusLedger.ts`）・`CHANGELOG.md` を段階ごとに更新する（CLAUDE.md）。

### 9-17. 段階 B の実装メモ（2026-10-28・v1.5.654・仕様との差分と補足）

実装の置き場所: フラグと古い画面の拒否＝`functions/src/snapshotStorageFormat.ts`、保存の判定・読み戻し検証・QR マージ・容量通知の純関数＝`functions/src/snapshotPartsWriter.ts`、
Firestore の配線＝`functions/src/index.ts`（`saveClassroomSnapshotAsParts`・`lectureSubmissionApi`・`pruneSnapshotParts`）。テストは `snapshotStorageFormat.test.ts`・`snapshotPartsWriter.test.ts`・
INV-14 マトリクスの「行（書き手）」。段階 A の暫定ガード（`parts-format-write-unsupported`・QR 取り込みの拒否）は撤去した。

| 項目 | 仕様（§9-3〜§9-10） | 実装 | 理由 |
|------|------|------|------|
| `saveAttempts.payloadHash` | 分割形式では全体ハッシュを入れる | **教室データ全体のハッシュのまま**。全体ハッシュは `compositeHash`、`hashScheme: 'parts-v1'` を併記 | `payloadHash` は同じ saveId の再送が同じ内容かを見る鍵（K-4 の冪等リプレイ）。送った内容のハッシュのままの方が形式に依らず比べられる |

### 10-4. 生成（教室ごとに順番に・目次は最後に公開・`functions/src/workspaceBackupWriter.ts`）

1. 会社（workspace）を全件読み、**会社ごとに try/catch で囲んで**順番に処理する（1 社の失敗をほかの社のその回へ広げない・AC-B19）。失敗は関数ログ＋開発者メール
   `auto-backup-failed`（会社ごとに 1 時間 1 通）＋手動実行の応答 `failures`。
2. 書く形式を設定で決める（§10-7）。教室別形式なら:
   - members・classrooms・classroomSnapshots を全件読む（`loadWorkspaceBackupSources`・教室の並びは classrooms の文書 ID 順＝旧形式と同じ）。
   - 教室ごとに「唯一の読み手 `readClassroomSnapshotPayload` で組み立て → 教室ファイル JSON → SHA-256 → gzip → Storage → Drive（設定時）→ メモリを解放」を**順番に**行う
     （1 教室ぶんのメモリ・AC-B18。全教室を並列にしない）。
   - **組み立てに失敗**（INV-14）: ファイルを書かず `missingClassrooms`（`assembly-failed`）に入れ、`snapshot-assembly-failed` で通知（今と同じ）。
     教室 ID に Storage のパスへ使えない文字がある（教室ファイルを作れない）ときも同じ扱い（その教室だけ除く・会社全体の時点は作る）。
   - **書き込みに失敗**: 1 回やり直し、だめなら `write-failed` として同じ扱い。その時点はほかの教室ぶんで公開する（AC-B9）。
   - **Drive の失敗**: 止めずに集め、要約の `googleDriveBackupStatus: 'failed'` と workspace 文書の `googleDriveBackupLastError` に残す（旧形式と同じ見え方）。
   - すべての教室が終わったら `index.json` → 要約（**ここで初めて一覧に出る**）→ 間引き（§10-6）。
   - 途中で止まった（時間切れ・メモリ不足・例外）: 要約が書かれないので一覧に出ない。残ったファイルは取り残しの掃除で消す（§10-6・AC-B10）。
3. 旧形式なら今までどおり（`runLegacyWorkspaceBackupForWorkspace`・全体 1 本・毎回 Drive の掃除）。全体 JSON の形は共有純関数 `buildWorkspaceBackupSnapshot`（教室ファイル・組み立て直しと同じ 1 か所・AC-B1）。
   旧形式の要約にも `layout: 'legacy'`・`classroomCount` を書く（同じ時点キーに教室別形式の要約が先にあっても読み手をこの回の形式へ向ける）。
4. 手動実行（`triggerWorkspaceServerAutoBackup`・開発者のみ・静音帯でも実行）は同じ経路（設定も同じ）。応答に `layout`・`failures` が増える以外は変わらない（AC-B20）。
   会社ごとの try/catch で例外が応答に乗らなくなった分、手動実行は `failures` が 1 件でもあれば従来どおり `internal` を投げて画面に失敗を出す。
5. 関数の設定は据え置き（生成 540 秒/2GiB・callable 512MiB）。段階 3 の実測のあとで下げてよい（任意）。

### 10-6. 保持と間引き（§8-2 を時点単位で適用）

- 保持の判定は今と同じ `shouldKeepWorkspaceAutoBackup`（時点の `savedAt` だけで決める・BK-1）。
- **間引きの単位は時点**（Q6）: 残さない時点は **教室ファイルと目次（`15min/{key}/` の下を全部）→ 要約**の順で消す（要約を先に消すとファイルが取り残される・AC-B12）。
  同じ時点キーに旧形式の 1 本と教室別形式のフォルダが混ざりうる（切り替えの前後に同じ 15 分枠で手動実行した・設定を戻した）ので、要約の `layout` に関係なく
  旧形式の 1 本（`storagePath` と旧形式の既定パス）と時点フォルダの**両方**を消す（無ければ何も起きない）。
- **取り残しの掃除**: 要約の無い `15min/{key}/` フォルダのうち、いちばん新しいファイルの作成から **1 日以上**たったものを消す（要約がある・作成時刻が読めない・未来のものは消さない）。
  `cleanupOldSaveAttempts` の巡回に**独立した時間予算（30 秒）**で相乗りし、Firestore 巡回より先に走らせる。**既定は空実行**（`WORKSPACE_BACKUP_ORPHAN_PRUNE_DRY_RUN` 未設定＝1・件数だけログ）。
  実物の件数をログで確かめてから `0` にして削除を有効にする。
- **Drive**（Q4）: 保持は Storage と同じ規則（`appProperties.savedAt` で判定・`.json.gz` は 400 日）。ファイル数が教室数倍になる（20 教室で約 1 万本）ので、
  教室別形式の回では **Drive の一覧と掃除を 1 日 1 回（JST 3:00 の回＝時点キーが `T03-00` の回。実行開始が 3:01 にずれても同じ回）**だけ行う（`isGoogleDriveDailyPruneRunAt`）。
  1 回の削除が約 55 回 × 教室数（20 教室で約 1,100 件）になるので DELETE は同時 10 件に抑える（落ちた分は翌日の回がもう一度拾う）。旧形式の回は毎回（今のまま）。
  掃除が 1 日 1 回なので Drive には最大でもう 1 日分の 15 分ファイル（1 社 約 73 × 教室数 × 0.75MB・20 教室で約 1.1GB）が余分に残る。
  30 教室で約 12GB（15GB の 80%）になるので、**25 教室を超えたら Drive の日次保持を短くするか再判断**（§10-12）。
- 復元前の控え（incident・90 日）は今の掃除（ファイルの作成時刻で 1 本ずつ）がフォルダでもそのまま効く。
- §8-1 #7・#8・#10 の行と §8-2 の容量の行は本節に合わせて更新した（2026-10-29）。

### 10-12. 後回しにしたこと（記録のみ）

- 会社ごとの分割実行（案 D・Issue #77）: 1 回の実行が 300 秒を超えたら、または 3 社目のときに着手。

- Drive の日次保持の見直し: 25 教室を超えたら再判断。

- 目次と教室ファイルから全体を組み立て直す CLI（`tools/`）: Drive からの復旧は教室ファイル 1 本を教室画面の JSON 読込で読めるので当面不要。必要になったら共有純関数 `assembleWorkspaceBackupFromClassroomFiles` を使う。

  数は少なく容量も小さいので放置。気になれば Drive の掃除に「要約の無い時点の削除」を足す。
