コマ表アプリでバグ修正をリリースした後、オーナーは高い確率で次の3点を追加で求める（2026-08-01/02 の
INV-06 未消化振替の一連で実際に要求された）。**言われる前に用意しておくと1往復で終わる。**

1. **なぜ防げなかったのか（構造要因）** … 「テストケースに入っていなかったのか」まで踏み込んで聞かれる。
   実際の答えは2回とも「テストは**あった**が fixture が実際の呼び出し側と違う形をしていて緑をすり抜けた」
   （①台帳 origin ありの振替しか置かない fixture ②時限トークン化前の形のままの fixture）。
   コードの内部モデルからケースを起こすと盲点がテストにも同じ形で写る、という説明が刺さった。
2. **他に同じことが起きるルートは無いか（横断監査）** … 1経路直して終わりにしない。実際に休日設定・
   非営業日化・全コマ削除・出席済み/振無休で追加の穴が見つかった。**実測（一時テストで真値を出す）で示す**と話が速い。
3. **本番で実際に何件動くのか（事前実測）** … リリース判断の材料。書き出し済みバックアップ JSON
   （`~/Downloads/コマ表アプリ_手動バックアップ_*.json`・緑が丘=88名/日大前=143名）を読み取り専用で読み、
   盤面と同じ関数（`buildMakeupStockEntries` 等）を vitest から回して件数を出す。Firestore へは触らない。

**オーナー自身が持っている強い観点**：「**在庫から出したコマ**と**盤面で移動して在庫を経由しなかったコマ**で
処理が変わっていないか」。過去のバグの急所がここで、レビュー観点として毎回効く（2026-08-02 も実在した）。
内部の道筋は違ってよいが**ユーザーから見た残数は必ず一致**させる、が確定ルール（`docs/spec-invariants.md` INV-06）。
